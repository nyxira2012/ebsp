## 1. 这一层要做成什么

一句话：**把"打一场仗"包装成一个黑盒服务——任何界面想打仗，交两份冻结的快照进来，拿一份完整战报回去；中间引擎怎么跑、演出怎么拼，外界一概不用管。**

它解决现在的三个烂摊子（2026-09-17 前后端对接评审实证）：

1. **装配散落**：装快照、拼结果的逻辑散在两处（调试接口 simulate 一套、PVE 战斗桥接 battle_bridge 一套），已经长得不一样；训练和竞技场再来只会更乱。
2. **战果丢弃**：PVE 打完仗把完整战斗过程当场扔掉，只回一个胜负数字，前端没法播。
3. **地基缺陷**：引擎用全局随机数（并发会话共享同一随机流，有污染且不可复现）；另有约定"由外层填写"却无人填写的悬空字段。

边界——它不管什么：**不管发奖**（掉落、信用点、入账归各玩法自己的结算）；**不改战斗规则**（引擎基本不动，只做小改）；**不是训练/竞技场玩法本身**（只是它们进战斗要走的门，玩法立项时各自立规格）。

## 2. 三件套

| 部件 | 职责 |
|---|---|
| **战报契约（contracts）** | 战报格式的唯一拼装点——Doc 14 那份时间轴 JSON 只在这里组装一次，序列化漏字段在结构上不可能 |
| **裁判（Engagement）** | 裁判本体：快照进 → 跑一次引擎和演出 → 战报出（过程 + 胜负 + 残血，三件出自同一次裁定） |
| **收发室（Entry）** | 唯一装配口：训练/PVE/PVP 三个界面都从这里交快照，别的地方不许自己攒 |

周边关系：

- **引擎与演出管线基本不动，只做小改**：接受指定随机流、补回合字段与开场/终局事件的生产。演出管线不改变换逻辑，仅模板竞标的随机源改为接受注入——影响战报内容的一切随机（圆桌掷点、技能触发掷点、演出模板竞标）统一收编进本场随机流（红线 3）。
- **PVE 会话是另一条内聚轴**（锁定小队、事件序列、经济结算、迷雾裁剪），保留不动。本层经窄接口与它握手：进——会话给的快照与上下文；出——残血交还写回、结算由 PVE 自己触发。

## 3. 战斗委托与战报

一场战斗的**委托**（进）：

- **两份冻结的输入快照**——值冻结，不是引用：委托建立后，格纳库的后续改动不影响已开打的这场仗；
- **场景标签**——这场仗从哪来（调试/训练/PVE/PVP，落到战报的入口标记 `route`）+ 战场环境引用（`scene` 槽规划升级为 `environment_id`：环境=配置化的战斗规则上下文——展示名+可选按侧授予效果/地形补正；编排层只透传 id 不解其义，效果在装配期注入参战快照。D9 方向，首个消费方为练习场训练力场，见 Doc 16 §5.3 与 Doc 1 §5.3）；
- **复现种子（可选）**——缺省随机生成并由后端记录，供日志与复现。

**战报**（出）两件产物，出自同一次裁定：

1. **完整战报**——Doc 14 全结构的时间轴；
2. **裁定**——结局（击破/判定/平局）+ 胜方 + 回合数 + 终局摘要
   （摘要即双方战后的耐久/能量/存活，供 PVE 写回；气力是场内资源，
   随战报走，不跨战斗写回）。

不变量（评审即打回项）：

- **裁定封闭**：开赛后委托不可再变，两件产物必出自同一次裁定；
- **事件点幂等**：同一事件点的接敌至多成立一次委托——裁定进行中或已裁定的重复/并发请求，返回终局摘要或明确拒绝；战报一律经重放端点，绝不产生第二次裁定；
- **失败原子**：裁定失败＝两件产物一件不出、残血不写回、事件点不消耗、结算不触发，接敌返回明确错误；
- **单次执行**：不提供战中干预——战中无操作是玩法设定（Doc 14 §1 纯演绎原则）。

预算：单场裁定同步完成即可返回，单场战报体积控制在数百 KB 量级（金样张顺带断言）。

## 4. 架构红线（评审即打回项）

1. **战报格式唯一拼装点**：时间轴响应的组装只存在于裁判 → 战报契约这条链，任何界面不得自行拼装——双装配点必然漂移（烂摊子 1 的病根）。
2. **战斗知识零泄漏**：PVE 与接口层不引用引擎/演出内部，只面向委托与战报。
3. **随机流可指定**：裁判持有本场的随机流，替换**一切影响战报的全局随机**（引擎圆桌、技能触发、演出模板竞标）——并发会话互不污染，同委托同种子必得同一战报（回放与将来竞技仲裁的地基）。
4. **悬空字段有主**：约定"由外层填写"的字段由本层统一填写，不依赖各界面自觉。
5. **装配单点**：三个界面的快照装配只走收发室——现存两处内联装配（simulate、battle_bridge）收编进来；将来训练/竞技场接入也只加来源适配，不再添装配点。

## 5. 战斗入口（门的设计）

真实游戏从 PVP / 训练 / PVE 三个界面进入战斗，共用同一裁判；差异全部收敛在"进"（快照从哪来）与"出"（战报谁消化）两端：

| 维度 | 训练（预留） | PVE 接敌（已有） | PVP 竞技场（预留，路线图 §8） |
|---|---|---|---|
| 己方快照来源 | **实时**：进入时从格纳库现构建（构建完即冻结） | **会话还原**：进副本时冻结的快照 + 残血注入 + 时间回能 | **对侧冻结**：对手布置时上传的防守快照 |
| 敌方快照来源 | 训练场景配置（靶机/木桩） | 模板 + 缩放，事件点实例化 + 敌方残血 | 防守方上传的防守快照 |
| HP/EN 初始 | 每次满状态 | 跨战斗持久（会话残血） | 每场独立满状态 |
| 种子策略 | 每次随机（重进=新对局） | 后端记录、不强制 | 锁定并持久化（同种子可仲裁） |
| 战后消化 | 无写回、无经济、不落记录 | 残血写回 + 玩法结算 | 战报落库 + 积分变动 |
| 重进战斗页 | 新对局 | 重放已裁定战报（P1 交付后生效；Doc 14 §9 第 5 条） | 重放已裁定战报 |

> 训练与 PVP 的**玩法内容不在本文档**——立项时各自立规格，届时经同一收发室接入。上表两列是"门"对它们的承诺，不是玩法的承诺。

消费方：

| 消费方 | 用法 |
|---|---|
| `POST /battle/simulate`（调试） | 静态配置 → 收发室（调试来源）→ 裁判 → 完整战报。请求语义不变（Doc 14 §2），战报入口标记=调试；调试设施——生产环境仅登录后暴露 |
| `POST /pve/sessions/{id}/engage` | PVE 供给上下文（会话冻结快照、事件、母舰）→ 收发室 → 裁判 → 残血写回 + 玩法结算；响应含终局摘要，完整战报经重放端点按需拉取（烂摊子 2 修复收敛为战报单一出口）。战斗知识零进入 PVE |
| 接敌确认卡（探索页事件卡） | 敌情预览走 PVE 自己的查询端点——敌情（敌方模板/缩放档/参考战力）与我方小队摘要纯 PVE 数据组装，**不触发裁定、编排层不参与**；迷雾边界照旧（暗雷触发前不可见，触发后/截停点可见） |

## 6. 关键设计决策

- **结算归属**：掉落、信用点、入账归各玩法的结算器，裁判只产出裁定与残血；战果结算界面归前端将来的规格。
- **复现与种子**：种子缺省随机生成、仅后端记录，**不入对外契约**——前端重放走已裁定战报，从头到尾用不到种子；入了契约就是对外承诺，不如留白。
- **敌方实例化时机**：事件点才实例化（模板 + 缩放 + 残血恢复），不必提前锁定；PVP 立项后敌方同样值冻结。
- **胜负表达**：结局（击破/判定/平局）与胜方正交表达（Doc 14 §7.1）；引擎内部的胜负布尔降级为内部兼容，不对外。
- **战报留存**：内存态。已裁定战报由消费该战的 PVE 会话侧暂存至该事件点消化完成（玩家离开或下一次推进）；进程重启/过期丢失时，重进战斗页降级为仅展示终局摘要。战报落库随"回看/申诉仲裁"立项再启——战斗记录表地基已在但当前无调用方，落库那天才填。
- **出战位**：PVE 接敌恒首机出战，出战位参数内部保留，多机出战立项时随入口扩展再暴露。

## 8. 测试与防漂移

- **金样张**：固定种子跑一场模拟，断言输出与 Doc 14 逐字段一致。**三处同步规则**：改字段必须先改 Doc 14 → 再改实现 → 重录样张。
