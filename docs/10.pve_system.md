## 1. 系统概述 (System Overview)
- **核心定位**：游戏最主要的 PVE 玩法，是玩家获取**装备**、提升战斗力、验证角色养成度的核心途径。
- **独立体验**：当前阶段为完全独立的单人 PVE 内容，不包含任何玩家间互动要素（暂不考虑其他玩家行为对地图、难度或资源的动态影响）。

## 2. 宏观探索：大区域 (Macro-Region Selection)
在进行讨伐战时，玩家首先需要在星图上选择要探索的“大区域”。

- **初期设定**：剧情初期的探索区域集中在太空基地周边，首批开放的经典大区域包括：
  - **废弃空间站 (Abandoned Space Station)**
  - **轨道电梯 (Orbital Elevator)**
  - **轨道墓场 (Orbital Graveyard)**
- **准入限制（母舰决定）**：
  - 玩家能否进入某个大区域，主要受到玩家当前**母舰性能**的限制。
  - 必须拥有符合区域环境要求的母舰（例如对应级别的环境抗性、跃迁引擎等级或特定的探索模块）才能解锁并进入高难度区域。

### 2.1 代码架构与实现方法 (Implementation Framework)
- **配置驱动**：使用 `RegionConfig`（基于 Pydantic 的配置数据模型）静态定义各大区域的准入硬性条件和基础消耗。
- **准入拦截器 (Validation Interceptor)**：在玩家请求进入区域的入口 API （如 `enter_region` endpoint）层面，调用前置依赖校验逻辑。通过比对 `UserSession` 中装载的 `MothershipSnapshot` 当前状态（抗性、引擎等级、装备模块）与 `RegionConfig` 需求阈值，决定是否放行。
- **进度持久化**：使用专用的数据库表（如 `user_pve_progress`）记录玩家在各大区域的有效解锁状态和最高通关记录，作为部分高阶区域树形解锁的硬性前置判定。

## 3. 微观探索：点阵小地图 (Micro-Map Exploration)
进入大区域后，具体的玩法表现为在一个点阵微观地图上的逐步推进与探索。

### 3.1 地图基础结构与移动机制 (Map Structure & Movement)
- **矩阵网格**：每层地图底层是一个标准的坐标点阵（例如：新手关卡基础底图为 **8x8 的点阵**）。每次生成的起点（着陆点）均为固定坐标。
- **受限的点阵移动（严格正交）**：玩家在点阵中**绝对禁止斜向移动**。所有的移动和线路生成**仅能沿着 X 轴和 Y 轴（即上、下、左、右四个正交方向）**进行。系统将点阵视为一张仅由正交轴连线构成的拓扑网，玩家只能沿着合法生成的**正交连线**一步步推进。
- **机动力由母舰完全决定 (Mothership-Driven Movement)**：
  - 玩家每次行动能跨越的“最大连线格子数”（如：默认 2 格，随着母舰提升可达 2-4 格）。
  - **派生逻辑**：直接通过读取 `MothershipData` 中的 `engine_level`（航行引擎等级）并结合可能存在的探索模块，换算出当次出击基础探路行动力。作为顶层宏观载具，由母舰全权掌控星系及微观点阵跨越距离，机体战斗属性不参与此阶段运算。
  - **约束机制**：即便机动力大于 1，在执行跨越式的正交移动轨迹时，若途经“强制阻挡节点”（如核心门锁、精英守卫明雷），系统将就地截断并中止剩余连线步数。玩家必须解除阻挡，方能再度推进。

### 3.2 代码架构与实现方法 (Implementation Framework)
- **地图关系模型抽象**：不使用二维数组，采用基于图论（Graph）的邻接表数据结构（`MapGraph`）表示地图节点。图顶点为 `MapNode(id, x, y, node_type, event_id)`，边直接存**目标节点 ID**（非强制对象引用，方便纯量序列化）。
- **移动逻辑与校验边界**：
  - 寻路请求一律交给服务端校验（BFS）。
  - **合法性判定屏障**：若目标不连通、途中强阻挡未清，或步数超出现在 `MothershipData` 指定的 `max_movement_points` 属性上限，则请求会依照设定好的**阻断策略**被响应。
  - **阻断策略 (Interruption Behavior)**：当多步移动跨线碰撞到了“明雷”等强制阻挡节点时，服务端并不仅仅是生硬拒绝请求，而是直接执行 **“自动分步截停移动 (Truncated Movement)”**，让玩家停在触发暗雷或阻挡卡口前那个安全的连通格子里，从而保证操作交互的顺畅连贯。
- **表现层与逻辑层彻底解耦**：采用“连通性决定移动”的方法，确保未来扩展任意复杂地穴时，只需增删边即可，无需重构底层移动探测逻辑。

## 4. 随机点阵地图生成方法论 (Random Map Generation Methodology)

为了在保证游玩体验可控的前提下提供足够的随机性空间，地图生成避免使用完全无逻辑的满撒点法，而是基于“**核心主干道先决 + 随机发散枝干 + 节点特征填充**”的设计手法。

### 4.1 第一步：预设拓扑模块拼图 (Tile-Based Preset Chunking)
完全在原子网格级别（逐格）进行随机游走极易产生“蛇形死锁”或“碎拼不可玩地形”，不仅测试难度极高，而且经常出现美感极差的迷宫。为规避此风险，我们将底层生成逻辑从“逐格随机”升级为**“预设模块拼装”（Preset Chuncks）**。
- **模板块 (Tiles)**：策划预先配置多种 $3\times3$ 或 $4\times4$ 的“手工设计小图块”（包含其出入口连接点和基础形状）。
- **拼接验证 (Layout Connection)**：生成器根据目标大地图规格（如 $12\times12$），随机抽取合适的图块进行“拼图连结”。只要边界点接口吻合，图块即可贴合。
- **保底连通性 (Guaranteed Paving)**：借助成熟的拼图（Wave Function Collapse 思想缩水版）算法，可以 100% 确保拼出来的骨架必定存在一条从 `Start` 到 `Boss` 的主干道，从物理层面上**直接铲除了“生成出死胡同无法通关地图”的恶性 Bug 风险**，极大地降低了 QA 和代码算法的兜底压力。

### 4.2 第二步：填充随机战术连线与分支 (Branching & Shortcuts)
在预拼装的稳定主通道框架骨骼上，再进行受控的**微观发散延展**。
- **动态横向连通（创建战术环路）**：在各预设图块的空余外缘接口之上，算法以极低概率向相邻缝隙拉扯“横向连线边（Edges）”。这打破了单一的枯燥长廊，形成了有闭环、允许多路包抄的复杂网状结构。
- **防破序校验 (Shortest Path Lock)**：每次尝试增加横向捷径时，系统挂载最短路径校验（如 Dijkstra）。若新连线导致 `Start` 到 `Boss` 的实际距离小于策划配置下限（比如不到 5 步即可偷渡），则果断废弃该捷径边。

### 4.3 第三步：分配障碍与节点事件 (Node Content Layout)
当整张地图的骨骼脉络（坐标点与有效连线）全部确立后，最后一步是把“血肉”塞进具体的格点里。
1. **必经之地的“拦路虎”（固定守卫战）**：在通往终点主干道的必经咽喉节点（Chokepoints）上，强制放置高难度的明雷守卫。玩家必须正面战斗获胜才能打通路线继续深入。
2. **高风险高回报的“死胡同”（宝箱节点）**：之前生成的树状分支的极限末端，会配置高价值的“宝箱节点”。为了平衡收益，在前往宝箱的必经分支连线上，系统会大概率生成对应的看守敌军，让玩家面临“为了拿极品装备，是否值得消耗血量去额外战斗一局”的经典抉择。
3. **改变地形的“可破坏障碍”**：这些障碍（如坍塌废墟、电弧拦截网）不一定需要战斗。它们多数分布在通往隐藏密室或战术闭环捷径的位置。玩家可以选择消耗特定的母舰能源或探索道具去“摧毁/破解”它，以此换取避开一整条高难度战斗路线的机会。
4. **空节点（安全区）**：没有任何阻碍要素的普通连通路段。

### 4.4 连续作战的状态继承 (Combat State Inheritance)
PVE 地图探索是一场**无情的消耗战**，这不仅对玩家生效，对场景中的中坚敌军同样生效。
**核心前置规则**：进入微观点阵地图探索期间，**绝对禁止**变更任何装备、技能、武器或出战机体列表。

- **敌方宿敌状态继承 (Enemy State Inheritance)**：为了强化“攻坚”与“策略”感，场景内的**固定守卫怪 (Elites) 与最终 Boss 怪，其每次战斗结束后的 HP 与 EN 同样会被写入会话持久化快照**。
  - **平局车轮战机制 (Draw & Relay Combat)**：本游戏中的单场自动战斗存在绝对的回合数上限（如 4-5 个回合）。如果面对极其抗打的血牛怪物，玩家无法在回合上限内将其彻底摧毁，该场战斗将以**“平局 (Draw)”**结束退出战斗画面，返回小地图。
  - 此时，由于**前排敌人的残存血量被强行保留在了系统中**，只要玩家队伍仍在地图存活且资源充足，就可以**停留在该地图节点上，紧接着对它发起第二轮、第三轮攻势（车轮战）**，直到将其击破。
  - *注：在此期间如果玩家队伍中任意机体被打爆（阵亡），则如同普通规则一样，立刻判定本次探索行动彻底失败 (Mission Failed)，直接踢出副本区域并惩罚清零，**绝不允许回母舰修整再回来打**的“僵尸流”作弊行为。*
- **己方 HP 与 EN 继承**：在点阵网络内，只要不出图（无论是清扫明雷暗雷），玩家出战队伍的 **剩余耐久度 (HP) 和剩余能量 (EN) 是跨场完全继承的**。
- **母舰的战间动态补给 (Real-time Mothership Supply)**：
  - 机体在地图节点之间移动或战斗胜出脱离后，无法自动瞬间回满状态。
  - 探索锁定了基础配置（即 `max_hp` 与 `max_en` 绝对恒定）。母舰工坊与补给模块的回血逻辑变更为**纯基于真实世界时间戳**的惰性恢复（例如每秒恢复 5 点 HP，具体数值由母舰提供）。
  - 玩家必须高度规划续航路径，利用时间差、杂兵吸血缓冲或是主动避战。

#### 4.4.1 代码架构与实现方法：双向状态与快照解耦 (State Decoupling Framework)
为了避免与“Doc 7：战斗快照仅限单局生命周期”设计与被动技能（如“最大HP提升10%”）产生生命周期计算耦合冲突，PVE 层在探索全程**绝不修改底层工厂，也不跨局混用僵尸 `MechaSnapshot`**。
- **引入双端轻量级 `PveEntityState`**：为出战队伍与敌方守卫挂载极简状态（仅包含上次战斗后的幸存绝对值 `db_hp`，以及 `last_combat_time`。因中途锁配置，`max_hp` 等为恒定推导量）。
- **惰性时间计算与防污染即将注入 (Pre-combat Hook & Explicit Binding)**：
  - 每次发起接战（触雷或打 Boss），统一向 `SnapshotFactory` 下发全新配置，生成**满血状态下**的双方纯净 `MechaSnapshot`。
  - 在正式切入 CombatEngine 前实施**拦截钩子计算**：根据公式 `战斗入场HP = min(Max_HP, DB_Saved_HP + (Now - Last_Combat_Time) * Mothership_Regen_Rate)` 结算母舰动态回血，直接通过快照结构原生暴露的接口传入 `current_hp` 与 `current_en`，覆盖初始状态。
  - **结构化战报抽提 (Structured Battle Result)**：战斗结束拔除所有的临时战场 `effects` 污染，`CombatEngine` 向外抛出包含当前最终存活者 `HP/EN绝对值` 的战报结构体。主干道上的 `PveEntityState` 接受战报覆盖残留血量并刷新 `last_combat_time`。这机制做到了在**没有真实持久层与装备工厂深度污染的状况下，极简且完美实现了“多轮回血条车轮战”与跨局回血**。

### 4.5 配置文件驱动体系 (Configuration-Driven Generation)
关于地图的所有控盘数据设计均通过外部“配置文件（Config）”进行管理设计，以确保策划可以随时调节强度。一张典型地图的配置文件涵盖：
- **地图规模**：基础网格宽高（X, Y）。
- **流程长度**：通往 Boss / 终点的最短步数阈值（N）。
- **强度属性**：固定守卫怪物的强度模板及出现数量上下限。
- **随机资源**：随机遇敌（暗雷）的触发概率、暗雷怪物的等级池。
- **动态掉落参数 (Dynamic ilvl Scaling)**：机制采用 **“区域基础值 + 战力/推进奖励”** 双轨制。
  - 配置文件中锁死该层基础掉落装等（如 `base_ilvl = 20`）。
  - 当队伍总战力或玩家在迷宫中未死亡持续战斗的“连胜场数”提高时，会轻微浮动向上加算隐性红利补缀（如 `final_ilvl = base_ilvl + [0~3]`）。既保证策划发奖的绝对控盘力，又给高练度玩家微弱的正反馈拉扯感。

### 4.6 地图生成环节代码实现方法 (Map Generation Framework)
- **预制拼装驱动 (Preset Tiling Module)**：取代原子级的随机游走代码核心，建立独立的 `TileMapGenerator`，读入策划配置化约的纯 JSON `$NxN$` “手工打磨碎块地形库”（包含出入口相对坐标），进行边界吻合匹配生成（类似于 Domino 拼接），完全降维杜绝了不可预测的代码发散迷宫风险点。
- **环路捷径生成与防破序校验 (Path Integrity Check)**：生成闭环分支和跳跃路时直接挂钩图论的“最短路径算法”（如 Dijkstra / A* 算法）。当核心组件尝试在节点 A 与 B 之间新建“横向连线边（Edges）”时，实时试演算 `Distance(Start, Boss)` 的最新权重；当新捷径导致结果 $< N$ 时，抛弃该捷径构造行为。
- **事件骨肉分离注入 (Event Injection)**：将结构的生成步骤（MapGraph 构建）和事件挂载（怪、宝箱）两核心逻辑切片。首先确保纯干干净净的骨架（仅包含坐标和连线）生成落地，再由配套的 `ContentPopulator` 组件扫描地图图元所有节点特征，以特定概率与配置池 (`EventPool`) 的权重映射完成内容填充。

## 5. 探索收益提取与死亡掉落惩罚 (Extraction & Death Penalty)
讨伐战期间获得的所有战利品都处于**“临时背包”（风险存放栈）**中，未确认落袋前都存在彻底丢失的风险。

- **物资有效化（落袋为安）**：必须达成以下三个条件之一，本次讨伐期间所获的所有**实物道具（装备、材料等）**才会正式进入玩家系统背包并保存：
  1. **小地图完全胜利**：成功击败当前大区域（或本层）的最终 Boss 完成该节点的结算。
  2. **成功撤离（离场事件）**：在地图关键节点（如入口或特定撤离通道）找到返航点，主动结束本次探索。
  3. **母舰干预（系统撤回）**：在探索进度中，无论处于什么位置，可选择支付**特定的代币/或一定比例已经获取的战利品（如交出本次 70% 收益）为脱离税**，唤来母舰强制撤场返航。

- **战败惩罚（实物清零与经济保留）**：
  - 如果玩家在任意一次讨伐战斗（无论是面临 Boss、明雷还是随机暗雷敌人）中被击败且无法复活，玩家队伍将被强制清出该副本区域（Mission Failed）。
  - **物品清零惩罚**：本次探索行动中在临时背包里获得的**所有随机掉落装备、宝箱实物资材将被直接清零遗失**（原有母舰和机体的状态受损但本身不会直接爆已有装备），鼓励玩家根据机体续航适时撤退。
  - **基础货币保留（防崩溃机制）**：为了避免与游戏的超高消耗经济系统（如千万级的母舰升级费）产生矛盾，玩家在单场暗雷或明雷战斗中**直接获得的“信用点 (Credits)”货币不列入风险临时栈，而是即时入账保留**。这样即使翻车，玩家当天的“刷钱打工”进度不会完全白费。

### 5.1 收益提取系统的代码实现方法 (Extraction Framework)
- **虚拟资产池结构管理 (Temporary Inventory)**：
  - 会话数据层维护独立的 `PveSession.pending_rewards` 属性（可以是 `List[Item]` 对象）。该数组始终只在当前活动缓存级存在，**绝对不直接往玩家角色的持久化背包表做 INSERT 提交**。
- **事务性提现固化 (Transactional Commit) 与幂等性边界**：
  - 核心结算控制器判断出玩家满足"有效结束条件"时，系统调用包装好的落袋结算指令 `InventoryService.add_items(user_id, pending_rewards)`（详见 Doc 12）。
  - 为了解决内存级别的会话态与 DB 正式背包数据写入带来的**网络挂起**或**内存回收失败**诱发的重领漏洞，此环节强制部署**“先入库后清理 + 强幂等防线”**策略：
    - **主键幂等前置拦截**：在向 DB 的实物资产表与流水表插入记录时，附带抛入当前批次的流水约束键（如 `PveSession.id` 建的约束）。若该会话曾被领选下发过一次，DB 凭借唯一索引直接把此请求弹回，从底层绝断了发包套取的重置伪造。
    - **严格隔离的数据事务**：随后在 DB 内部开启完整 Transaction 来批量保存全部材料、图纸装备，只要途中有断流，立刻全量回退，阻击赃物产生。
    - **后置销毁缓存态**：只有捕获到 DB 确切反馈 `Commit Success` 的钩子后，内存中的 `PveSession` 对象以及对应持久化在 DB 里的 PVE 会话记录才会被真正擦除（`del` / `DELETE`）。即便这步销毁因为宕机等失效了，玩家重试依然被 DB 流水表的幂等防线完美拦截。
- **即时收益旁路机制 (Instant Non-Risk Rewards)**：
  - 在完成每单次明/暗雷战斗结束的结算 API 中，涉及信用点的部分单独走 `UserService.add_credits()` 完成 DB 级的即刻加钱提交，直接绕开 PVE Session 的成败束缚，提供安全保底机制。
  - PVE 中途溃败，只需触发销毁当前的 `PveSession` 内存对象与 DB 会话留存表，该笔虚拟悬停背包也就完成了符合设定的“惩罚性自然清零”，极度干净且没有任何多余补丁开销。

## 6. 服务器资源消耗与内存管理 (Server Resources & Memory Management)

对于大规模的随机地图生成，由于其核心仅为“数据节点”而非复杂的3D物理模型或海量实体，只要数据结构设计合理，**不会对服务器造成庞大的运算和内存压力**。

### 6.1 地图数据结构的轻量化 (Lightweight Data Structure)
- **纯粹的拓扑图**：服务器端不需要存储任何可视化的“地图包”，只需在内存中维护一个轻量级的图数据结构（Graph）。
- **节点与边**：一个 `8x8` 的矩阵最多只有 64 个节点对象。每个节点对象仅保存基础属性，如：坐标 `(x, y)`、节点类型（空地/守卫/宝箱等）、以及与其相连的邻居节点引用的列表。
- **序列化存储**：即使是更大的地图，其拓扑结构也能被极致压缩为一个很小的 JSON/二进制字符串进行网络传输或落盘。单个副本实例的地图数据在服务器内存中只占用极小的 KB 级规模。

### 6.2 内存释放与生命周期管理 (Lifecycle & Garbage Collection)
为了支持大量玩家同时开启讨伐战副本，服务器需要对这些微缩地图实例进行严格的生命周期管控：

1. **按需实例化与懒加载 (Lazy Loading) / 多层切换清除**：
   - 玩家在主界面或星图时，不加载任何讨伐战地图数据。
   - 只有当玩家点击“进入区域”的一瞬间，服务器才会调用地图生成器，运算出当前层的图状结构并挂载到玩家的 `PveSession`。
   - 多层地图**不会一次性生成**。玩家打通第一层触碰传送点进入下一层时，服务端不仅立即按配置生成下一层图谱，且必定于此时**强制注销抹除并 Garbage Collect 第一层节点状态的全部内存及硬盘索引**（因探索是单向推进，不允许回头）。

2. **静默休眠与内存换出 (Swapping)**：
   - 讨伐战是完全单人的 PVE，如果玩家在中途下线，或者长时间停留在某个节点没有进行移动和战斗操作（例如挂机），服务器不应该让这个地图实例一直死占内存。
   - **机制**：当副本实例超过一定时长（如 15分钟）无心跳交互，服务器会将当前的轻量级地图结构（包含哪些怪打死了、哪些宝箱开了）及奖励对象序列化后写入数据库专用的 `pve_sessions` 暂存表中，并把内存中的所有地图对象彻底销毁。
   - **重连原则 (Reconnection Principle)**：断线并重新上线一律采纳**单层存档继续 (Continue Layer)** 逻辑。只要该 `pve_sessions` 记录的 TTL（例如 24 小时）未强制过期且未触发死档废弃（结算或者被击毁），不论下线间隔多久，一律从该 DB 记录反序列化瞬间恢复所在层的精准地图状态（含已探开的迷雾、当前的血量），杜绝靠反复拔网线来重置暗雷和地图结构的作弊行为。

3. **彻底销毁与垃圾回收 (Destruction)**：
   - **正常结束**：玩家击败 Boss 结算、主动撤离或战败强制弹出，副本生命周期宣告终结。服务器在结算发奖后，立即解绑该地图实例与玩家会话的引用，让其被语言层面的垃圾回收器（如 JVM/V8 等的 GC）彻底清理。
   - **异常兜底（TTL机制）**：为防止断线重连失败造成的“内存泄漏影子副本”，所有写入缓存的副本存档都带有绝对生命周期（例如 24 小时 TTL）。超时后数据库层面将强制抹除该记录，确保永久没有玩家认领的死档不会无限堆积。

### 6.3 服务器资源代码与内存控制架构 (PostgreSQL Active Cache)

> **[开发阶段补充] 渐进式数据库落地策略**
> 针对 UNLOGGED TABLE 等 PostgreSQL 专属的高级缓存特性，**将在后续重构阶段引入真正的 PostgreSQL 数据库时予以实装**。
> 在**初期开发阶段**，为了快速跑通 PVE 核心逻辑，系统将继续使用当前极简的关系型数据库（如 SQLite）进行基础表的增删改查测试。这一策略确保了业务主循环的落成不会被数据库的基础架构铺设所阻塞。

为了应对大体积 JSON Blob 在玩家踩格子时引发的高频写库与事务雪崩，本系统摒弃传统纯内存/Redis方案，完全复用 Postgres 原生机制进行**读写分离控制**。

- **UNLOGGED TABLE 核心缓冲器 (High-frequency Active Cache)**：
  - 在关系型数据库中建立专门用于热点 PVE 进度缓存的无日志表 `UNLOGGED TABLE pve_active_sessions(user_id, session_data_json, last_combat_time, updated_at)`。
  - **规避 WAL 磁盘磨损**：由于 `UNLOGGED` 表跳过了写前日志 (Write-Ahead Log)，对其进行 `UPDATE JSONB`（如地图点击跨越、迷雾解锁）的高频微小动作速度等同于写内存，彻底释放物理 I/O 和进程锁压力。虽然其代价是在数据库崩溃时该表数据会被清空，但对于容错性极好的探索式 PVE（顶多退回该层起点）完全可接受。
- **检查点状态同步 (Checkpoint Persisting)**：
  - 当发生三大关键事件时（**跨层地形跃迁/击败Boss**、**玩家主动撤退提现**、**用户因掉线/下线心跳触发挂起**），系统才会发起标准事务，将轻量的活跃态 JSON 序列化移交进真正持久且安全的 `pve_sessions` 常规表中锁死。
  - **资产幂等强固化**：在进行物资结算发包时，附带抛入当前批次的流水约束键（Idempotency Key），开启完整 Transaction 处理装备/图纸。遭遇宕机全量回退，彻底阻断了任何重放伪造和“网线复制”的漏洞。
  - **状态无缝流转 (Stateless Reconnection)**：基于 UNLOGGED 与持久表互通的纯 DB 架构轻松支持微服务横向扩展。玩家无论连上哪个后端进程节点，只需一个轻量级 `SELECT` 就能100%无损反序列化局内关键变量。

## 7. 开发实施路径与风险应对 (Implementation Plan & Risk Mitigation)

前文的设计在落地到实际代码库时，必然会面临**系统耦合、幂等性缺陷与状态机测试困难**等落地风险。为了不让这些风险阻塞开发，必须采取**“分阶段落地 + 接口Mock”**的方法论进行处理。

### 7.1 核心风险评估
您指出的 6 个问题**百分之百会影响开发进度**，如果不加干预，它们会导致整个 PVE 系统变成一个需要等待所有周边系统（如母舰、背包、基础架构）全量完工才能测试的“宇宙级巨石模块（Monolith）”。

### 7.2 应对策略：三阶段破局法 (Phased Strategy)

#### Phase 1: 核心引擎骨架 (Core Engine & Mocking)
在周边系统（尤其是母舰和背包）未就绪时，强行开发只会导致被阻滞。
- **应对“母舰缺失”(风险5) 与“快照交互”(风险1)**：
  - **Mock 驱动**：在 PVE 模块内部建立一个假的 `MockMothershipService` 和 `MockMechaState`。
  - 发动战斗前，不走真实的数据库取装备和母舰状态，而是用假数据搓出 `MechaSnapshot`。
  - 这阶段的目标是**跑通大地图探索 -> 遭遇战 -> 血量百分比扣除 -> 继续探索**的极简纯内存状态机（State Machine），不连接任何真实的 DB 持久化。

#### Phase 2: 基础设施接驳 (Infrastructure Hookup)
当单机版的状态机跑通后，开始解决脏数据与保存问题。
- **应对“幂等性缺口”(风险2) 与“持久化冲突”(风险4)**：
  - **先造轮子再造车**：在写 PVE 结算逻辑前，**先停下来去全局工具类中实现 DB 的幂等性装饰器/中间件（Idempotency Key Manager）**。这不仅是 PVE 需要的，更是整个游戏防刷的基建。
  - **心跳与断线对齐**：使用依赖注入（DI）将 `PveSessionManager` 与 DB 连接。实现“走格子仅改内存，打完怪必须强刷一遍 `pve_sessions` 表”的混合策略。此时引入真实背包系统的写入（配合已写好的幂等件）。

#### Phase 3: 预设区块与降维打击 (De-risking Map Gen Engine)
- **应对“地图生成死锁与不可控迷宫”(风险3)**：
  - **全面屏弃原子随机游走**：如果让代码自己一个个点去连，不仅存在无穷的算法死角与 QA 随机瞎盲测试，且地形设计很容易变得极为无聊空洞。
  - **启用预设手工地块库拼接 (Tile Chunk Assmebly)**：必须实施第 4 章新敲定的 `TileMapGenerator` 思路。让策划或程序在 JSON 里死写好各种设计绝佳、必定连通的（$3\times3$, $4\times4$) 地形碎片基底，算法只负责做“拼图拼装接口”，通过降维打击彻底铲除整个核心系统的崩坏几率与随机性覆盖测试成本。
