## 1. 系统概述 (System Overview)

- **核心定位**：游戏最主要的 PVE 玩法，是玩家获取**装备**、提升战斗力、验证角色养成度的核心途径。
- **独立体验**：当前阶段为完全独立的单人 PVE 内容，不包含任何玩家间互动要素。
- **架构总览**：本系统采用"**大-中-小**"三级空间套盒架构驱动探索推进，配合"**战斗状态继承 + 资产风险结算**"构成完整的内循环。

### 三级空间架构概览
| 层级 | 名称 | 举例 | 职责定位 |
|---|---|---|---|
| **L1 战略层** | 副本 (Instance) | 废弃空间站、轨道墓场 | 区域背景与母舰准入门槛 |
| **L2 战术层** | 子区域 (Zone) | 空间站码头、空间站指挥所 | 据点解锁进度与主题分区 |
| **L3 执行层** | 随机事件序列 (Micro-Sequence) | 8~12 个连续事件 | 战斗内循环与资源博弈 |

## 2. 战略层：副本选择 (Instance Selection)

副本是全局进度的里程碑，负责定义探索的场景基调、物品产出阶级与母舰准入条件。

### 2.1 区域设定

初期开放区域集中于太空基地周边：
- **废弃空间站 (Abandoned Space Station)**
- **轨道电梯 (Orbital Elevator)**
- **轨道墓场 (Orbital Graveyard)**

高阶副本则需要玩家完成前置探索目标后，由进度系统在星图界面逐步点亮开放。

### 2.2 준入限制 (Entry Validation)

能否进入特定副本，受制于母舰的硬件实力：
- **母舰级硬性拦截**：要求母舰具备对应的引擎等级或指定的环境抗性模块。否则于入口 API 处直接驳回请求，不进入任何排队或预加载流程。
- **进度树型解锁**：高阶副本需要玩家在低阶区域达成关键目标（如击杀特定精英），方才在前端星图上可见并开放。

### 2.3 配置驱动 (Configuration-Driven)

副本的全部参数以静态配置文件承载，涉及：
- 准入硬性条件（引擎等级阈值、抗性模组 ID）
- 全区域的基础掉落品级 `base_ilvl`
- 下辖的所有 L2 子区域（Zone）节点定义，详见第 3 章。

---

> **状态层**：`user_pve_progress` 数据库表，按副本记录解锁状态和最高通关纪录。
>
> **行动层**：`PveEntryService.enter_region()` 检查准入条件，验证通过后建立 `PveSession`；拒绝时返回标准的"准入错误"响应。
>
> **事件处理层**：准入失败视为 L1 层错误，由本层负责处理，不向下穿透至战斗执行层。
>
> **界面控制层**：星图界面按玩家的 `user_pve_progress` 状态决定各副本的点亮/置灰/锁定显示；未解锁的区域须同时展示解锁条件提示。

## 3. 战术层：子区域推进 (Meso-Zone Progression)

在选定副本进入后，玩家面临该区域内多个具有主题的子场景节点，这一层是"战术选择与主线进度"的容器。

### 3.1 线性梯次解锁 (Sequential Unlock)

子区域之间遵循明确的依赖链。以废弃空间站为例：
- 初期仅开放"**空间站码头**"。
- 完成码头子节点通关后，"**空间站指挥所**"解锁。
- 斩获指挥所后，更深处的节点才开放选择。

这种设计目的在于：为玩家提供明确的中期目标感（而非一进入副本就面对一盘散沙），根据不同的节点呈现不同的变化（如：随着节点推进自然呈现怪物等级上升、掉落品质提高的成长曲线）。

### 3.2 概率型隐藏节点 (RNG Hidden Zones)

在满足特定触发条件时（如区域刷新、完成普通节点后），系统以一定概率在前端战术界面额外呈现一个**隐藏节点**（如"空间站仓库"）。

隐藏节点通常具有高度差异化的体验：战利品高度集中的纯收益型、或者是绕过了普通进度的精英刷新。其核心价值在于：为重复刷图的玩家提供可期待的随机惊喜，保持长期游玩动力。

### 3.3 子区域配置结构 (Zone Configuration)

每个子区域作为顶层 `RegionConfig` 的子项嵌套定义，包含：
- 所属副本 `region_id` 与自身 `zone_id`
- 前置解锁条件 `unlock_requires`（填写前置 `zone_id`，首发节点为 `null`）
- 隐藏节点的概率出现参数 `spawn_chance`（仅隐藏节点有此字段）
- 专属的事件生成配置集（见第 4 章，包括事件数量范围、事件类型权重及敌方模板池），同一副本内各子区域拥有独立差异化的怪物池与权重，呈现主题化场景差异。

---

> **状态层**：`user_pve_progress` 在副本键下以字典形式精细记录各节点的 cleared/locked/hidden_available 状态，例如 `{"abandoned_station": {"dock": "cleared", "command_post": "locked"}}`。隐藏节点的刷新结果在本次会话期间强制持久化，防止反复退出重进刷新。
>
> **行动层**：`ZoneSelectService.enter_zone()` 负责校验选定节点的解锁状态、以隐藏节点概率决策并结果固化，校验通过后调用执行层生成事件序列。
>
> **事件处理层**：节点未解锁为 L2 层错误，由本层统一拦截返回，不向下穿透。节点通关事件由执行层完成后上报，由本层更新 `user_pve_progress` 中的解锁链。
>
> **界面控制层**：战术界面展示当前副本内所有子节点的状态地图；已清除节点附有标记与已获战利品历史；概率刷出的隐藏节点须以明显视效区分于常规节点（如特殊光圈+倒计时）。

## 4. 执行层：随机事件序列 (Micro-Sequence Execution)

进入子区域后，实际游玩进入执行层：系统生成一条随机事件序列，玩家逐一推进并承担战斗结果，直到序列完成或中途撤退。

### 4.1 序列生成机制

系统在进入节点的瞬间**一次性**生成完整的事件序列——共 N 个事件（N 由所在子区域的配置 `event_count_range` 决定，典型值为 8~12）。序列在服务端以当前会话存档，玩家在本次探索中无法更改种子、重置序列，彻底杜绝靠断线重置获得更好事件组合的作弊行为。

**生成逻辑**：
1. 按配置范围 `event_count_range` 随机确定本次序列总长度 N。
2. 将第 N 个位置固定写死为 `BOSS_COMBAT` boss 战，并绑定本区域的 `boss_template`。
3. 对前 N-1 个位置，依据本区域的 `event_weights` 权重分配，通过加权随机抽取确定各事件类型。
4. 对所有战斗类型事件，从对应的 `normal_pool` 或 `elite_pool` 中抽取具体的敌方机体模板 ID，完成序列封装。

### 4.2 推进原则

序列完全线性，不存在分叉路径：
- 玩家每次操作推进后，系统仅对外暴露**当前一个**事件的信息（脱敏处理，对后续事件一律不透明），在视觉上制造"翻牌盲盒"的心理博弈感，促使玩家基于当前 HP/EN 续航状况做出是否继续深入的风险决策。
- 不允许后退，只能向前推进或主动撤退。
- 玩家在当前事件未结算（如战斗打平，待下一轮车轮战）前，不能推进至下一格。

### 4.3 事件类型详解

| 事件类型 | 枚举值 | 行为规则 |
|---|---|---|
| 普通战斗 | `COMBAT` | 遭遇随机巡逻队，须战斗。 |
| 精英战斗 | `ELITE_COMBAT` | 强制接敌，无逃脱选项，必须打至"胜/平/败"之一结果。 |
| Boss 战斗 | `BOSS_COMBAT` | 序列终结挑战，强制接敌，胜利则触发完整结算通关。 |
| 获取 | `LOOT` | 无战斗，直接触发宝箱拾取流程，物资进入临时背包。 |
| 随机事件 | `EVENT` | 文字选择题节点，可能带正向效果（恢复 HP/EN）、负向效果（扣除资源）或特殊撤退通道。 |

### 4.4 API 交互安全：脱敏与全栖幂等 (Security & Idempotency)

- **数据脱敏 (View Masking)**：服务端预生成完整序列，但推进响应遵循"**单步暴露**"原则。仅下发当前索引事件的类型，屏蔽后续瞎想空间，杜绝抓包作弊。
- **并发与断网防抖 (API Idempotency)**：由于网络重试可能导致重复发包污染状态，执行层的核心接口（如 `/advance`, `/engage`）强制基于 **乐观锁/递增版本号** 作为幂等校验基准。例如：客户端发起 `/advance` 必须携带 `expected_index=3`，服务端发现当前实际 `index=4` 即判定为重试或过期请求，拦截并下发同步状态，杜绝"多推了一步"或"扣了两次血"的严重系统事故。

---

> **状态层**：`EventSequence` 包含 `List[PveEvent]`（事件列表）与 `current_index`（当前推进索引）。整个 `EventSequence` 在进入节点时序列化写入 `PveSession.session_data`，每次推进后同步更新 `current_index`。
>
> **行动层**：`EventSequenceGenerator.generate(zone_config)` 负责权重生成；`PveSession.advance()` 负责推进索引校验并返回当前事件描述；`/advance` API 端点负责接收前端操作并编排上述两个组件。
>
> **事件处理层**：序列完成（即推进至 Boss 并胜利）时，向上通知战术层更新节点解锁状态，并触发结算流程（见第 6 章）。

## 5. 连续作战的状态继承 (Combat State Inheritance)

PVE 探索是一场**无情的消耗战**。进入事件序列探索期间，**绝对禁止**变更任何装备、技能、武器或出战机体列表。

### 5.0 三层快照架构总览 (Three-Layer Snapshot Architecture)

为防止作弊并支持跨场状态继承，系统采用**三层快照架构**。每层快照职责明确，生命周期独立，通过数据流转实现状态同步。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        PVE 三层快照架构                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ Layer 1: 配置快照 (Locked Config)                                │    │
│  │ ─────────────────────────────────────────────────────────────  │    │
│  │  时机: 进入PVE区域瞬间（仅执行一次）                             │    │
│  │  内容: 完整的 MechaSnapshot 列表                                  │    │
│  │        • 机体基础属性（HP/EN/攻击/防御等）                        │    │
│  │        • 装备列表（含随机词条）                                   │    │
│  │        • 技能/武器配置                                            │    │
│  │  存储: PveSquadState.locked_config (JSON)                        │    │
│  │  作用: 防逃逸 — 隔离外部装备变更，与母港数据完全解耦              │    │
│  │  生命周期: 整个PVE会话期间（只读，不可修改）                       │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                              ↓ 战前注入                                  │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ Layer 2: 状态代理 (PveEntityState)                               │    │
│  │ ─────────────────────────────────────────────────────────────  │    │
│  │  时机: 每场战斗后更新                                            │    │
│  │  内容: { current_hp, current_en, max_hp, max_en,                 │    │
│  │         last_combat_time, is_alive }                             │    │
│  │  存储: PveSquadState.members: List[PveEntityState]               │    │
│  │  作用: 状态继承 — 记录跨场血量/能量变化                           │    │
│  │  生命周期: 整个PVE会话期间（每次战斗后更新）                       │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                              ↓ 战前注入                                  │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ Layer 3: 战斗快照 (MechaSnapshot) — 战斗引擎使用                 │    │
│  │ ─────────────────────────────────────────────────────────────  │    │
│  │  时机: 每场战斗前动态生成                                        │    │
│  │  生成公式: Layer1(配置) + Layer2(当前血量) + 母舰补给恢复         │    │
│  │  存储: 单次战斗期间（不持久化）                                   │    │
│  │  作用: 实际战斗计算                                              │    │
│  │  生命周期: 单次战斗（战斗结束即销毁）                             │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                              ↓ 战后提取                                  │
│                       更新 Layer2 (current_hp/current_en)              │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 数据结构对照表

| 层级 | 代码类型 | 存储位置 | 可变性 |
|:---|:---|:---|:---|
| **Layer 1 配置快照** | `Dict[str, Any]` | `PveSquadState.locked_config` | 只读 |
| **Layer 2 状态代理** | `PveEntityState` | `PveSquadState.members[]` | 每战后更新 |
| **Layer 3 战斗快照** | `MechaSnapshot` | 战斗引擎内部（不跨场传递） | 临时创建 |

#### 核心设计原则

1. **单向数据流**：Layer 1 → Layer 2 → Layer 3，严禁反向修改
2. **物理隔离**：Layer 1 的深拷贝确保外部装备变更不影响副本内数据
3. **状态最小化**：Layer 2 只存储必要的百分比/绝对值，不携带完整属性
4. **按需组装**：Layer 3 在每次战斗前动态组装，战斗完成后立即丢弃

---

### 5.1 己方 HP 与 EN 的跨场继承

玩家出战队伍的**剩余耐久度 (HP) 和剩余能量 (EN) 在序列内跨场完全继承**。每次战斗或遭遇事件结束后，战斗引擎返回最终存活状态的 HP/EN 绝对值，PVE 层提取后更新 **Layer 2 `PveEntityState`**，作为下一场战斗的入场血量基准。

### 5.2 母舰的战间动态补给 (Real-time Mothership Supply)

机体在事件之间无法瞬间回满状态。母舰补给模块的回血逻辑基于**服务端权威时间戳 (Server-side Timestamp)**的惰性恢复计算：

**补给计算公式**（在 Layer 3 战斗快照生成时应用）：
```
恢复量 = (当前时间 - PveEntityState.last_combat_time) × 母舰回血速率
实际入场HP = PveEntityState.current_hp + 恢复量
实际入场EN = PveEntityState.current_en + 恢复量
```

**安全红线**：绝对不信任且不收录客户端传回的任何业务时间参数，彻底封堵玩家通过修改本地设备时钟来实现秒回血的"时间刺客"作弊行为。

玩家可主动利用时间差（等待恢复）或节点选择（优先走 LOOT 房回避战斗）来管理续航。

### 5.3 精英/Boss 的宿敌状态继承

`ELITE_COMBAT` 和 `BOSS_COMBAT` 类型的固定敌方实体，其血量状态**同样在车轮战多轮次间继承**：

- 本游戏单局自动战斗有绝对回合上限（根据配置文件）。
- 无法在上限内击败敌方时，战斗以**"平局 (Draw)"**收场，玩家可在当前格发起下一轮车轮战（消耗自身 HP/EN）。
- 敌方血量状态同样通过 **Layer 2 `PveEntityState`** 记录，在多轮战斗间持久化。
- 若玩家队伍中任意机体在车轮战期间被击毁（阵亡），立即判定**探索行动彻底失败 (Mission Failed)**，直接踢出副本。**严禁回母舰修整后再回来继续打当前节点**的"僵尸流"设计。

### 5.4 技术实现：战前注入与战后提取

#### 5.4.1 战前注入流程 (Pre-combat Injection)

每次接战前，系统按以下顺序组装 **Layer 3 战斗快照**：

```
Step 1: 从 Layer 1 读取配置蓝图
        ↓
        locked_config["mechas"][i] → 获取完整的 MechaSnapshot JSON

Step 2: 计算 Layer 2 状态恢复量
        ↓
        regen_hp = (now - PveEntityState.last_combat_time) × mothership.hp_regen_per_min
        regen_en = (now - PveEntityState.last_combat_time) × mothership.en_regen_per_min

Step 3: 注入实际入场血量
        ↓
        combat_snapshot.current_hp = min(max_hp, PveEntityState.current_hp + regen_hp)
        combat_snapshot.current_en = min(max_en, PveEntityState.current_en + regen_en)

Step 4: 提交战斗引擎
        ↓
        战斗引擎使用注入后的快照进行计算，不感知 PVE 层逻辑
```

#### 5.4.2 战后提取流程 (Post-combat Extraction)

战斗引擎完成后，PVE 层接收标准化战报，执行提取：

```
Step 1: 接收战斗结果
        ↓
        outcome: WIN / LOSE / DRAW

Step 2: 提取最终状态
        ↓
        从战报中提取每个机体的最终 current_hp / current_en

Step 3: 更新 Layer 2 状态代理
        ↓
        PveEntityState.current_hp = 战报最终值
        PveEntityState.current_en = 战报最终值
        PveEntityState.last_combat_time = 当前服务端时间戳
        PveEntityState.is_alive = HP > 0

Step 4: 分支处理
        ↓
        WIN → 清除当前事件，推进序列索引
        DRAW → 保留当前事件，更新双方 Layer 2 状态（准备车轮战）
        LOSE → 触发 Mission Failed 流程
```

> **数据结构声明**：
> ```python
> class PveEntityState(BaseModel):
>     """Layer 2: 状态代理 — 轻量级血量容器"""
>     entity_id: str                    # 机体实例 ID
>     current_hp: int                   # 当前血量（绝对值）
>     current_en: int                   # 当前能量（绝对值）
>     max_hp: int                       # 最大血量（从 Layer 1 复制）
>     max_en: int                       # 最大能量（从 Layer 1 复制）
>     last_combat_time: float           # 上次战斗结束时间戳
>     is_alive: bool = True
>
> class PveSquadState(BaseModel):
>     """PVE 队伍状态容器 = Layer 1 + Layer 2"""
>     members: List[PveEntityState]     # Layer 2: 每个机体的状态代理
>     locked_config: Dict[str, Any]     # Layer 1: 战前锁定的完整配置快照
>         # 格式: {"mechas": [{"mecha_id": str, "snapshot": MechaSnapshot, ...}]}
> ```
>
> **行动层**：`BattleBridge.engage(session, event_index)` 负责拉取 Layer 1 配置和 Layer 2 状态，执行战前注入，调用战斗引擎，提取战报并更新 Layer 2。
>
> **事件处理层**：胜利时 `PveEvent.cleared = True` 并推进序列索引；平局时保留事件、更新双方 Layer 2 状态；败北时触发 Mission Failed 流程（销毁 `PveSession`，清空临时背包）。

## 6. 探索收益提取与失败惩罚 (Extraction & Death Penalty)

讨伐战期间所获全部战利品处于**"临时背包（风险存放栈）"**中，未落袋前均存在丢失风险。

### 6.1 物资有效化条件（落袋为安）

实物道具（装备、材料）的永久入库，必须达成以下三个条件之一：
1. **完整通关**：成功推进并击败序列末尾的 Boss，触发区域全额结算。
2. **有效撤离**：在 `EVENT` 类型事件中出现"撤离通道"选项时，主动选择撤出以带走全部已获物资。
3. **母舰强制撤回**：在任意探索进度位置，玩家主动支付"脱离税"（占本次已获战利品的一定比例，具体由母舰等级决定），换取母舰介入带走剩余物资。

### 6.2 失败惩罚规则

玩家队伍机体阵亡，即判定探索失败：
- **实物清零**：本次探索获取的临时背包内所有装备和材料，直接清零，不进入玩家背包。
- **游戏货币即时保留**：单次战斗获得的游戏货币走独立旁路即时确认入账，不受实物清零的影响。这是防止玩家因一次失误导致当日刷图完全白费的底线兜底机制。

### 6.3 提现安全框架

- **临时背包的存活范围**：`PveSession.pending_rewards` 属性只在会话活跃期间存在于内存中，断线即清零。
- **幂等双重保险**：结算入库前，先查 `PveRewardLedger` 有无该 `session_id` 流水（应用层软校验），再通过该表的 `session_id` 唯一索引作为数据库层硬拦截（防止并发双重结算）。
- **事务原子性**：所有物资的批量写入包裹在完整数据库事务内，中途任何环节失败则全量回退，确保不出现"货到一半"的脏数据。
- **后置销毁**：仅在数据库确认提交成功后，才销毁内存中的 `PveSession` 对象。

---

> **状态层**：`PveSession.pending_rewards`（临时背包 List）、`PveRewardLedger`（流水表，幂等硬防线）。
>
> **行动层**：`RewardController.add_pending_loot()` 战后暂存；`RewardController.finalize()` 结算时驱动幂等校验 + 事务批量写入 + 流水记录。`UserService.add_credits()` 负责信用点的即时旁路入账。
>
> **事件处理层**：胜利/撤退/败北三个路径各触发不同的结算策略；失败路径仅需销毁 `PveSession`，临时背包随之自然清零，无额外操作成本。
>
> **界面控制层**：通关/撤退完成后，向玩家展示"结算界面"：列明本次获得的全部物资清单及实际入库结果。母舰干预撤退时，额外展示"脱离税扣除明细"。

## 7. 会话持久化与内存生命周期 (Session Persistence & Lifecycle)

### 7.1 会话数据结构的轻量化

事件序列方案大幅降低了服务器存储成本：整个探索进度仅需维护 `EventSequence`（事件列表 + 当前索引）、`PveSquadState`（Layer 1 配置快照 + Layer 2 状态代理）和 `pending_rewards`（临时背包）三个核心对象，可轻易压缩为小型 JSON 字符串落盘。

### 7.2 会话生命周期

| 阶段 | 触发时机 | 行为 |
|:---|:---|:---|
| **实例化** | 玩家进入子区域 | 生成事件序列，创建 **Layer 1 配置快照**（深拷贝），建立 `PveSession` 对象持驻内存 |
| **推进刷新** | 每次推进事件 | 更新 `EventSequence.current_index`，仅更新内存对象 |
| **战前注入** | 每次进入战斗前 | 从 Layer 1 + Layer 2 + 母舰补给计算生成 **Layer 3 战斗快照** |
| **战后提取** | 每次战斗结束后 | 提取最终 HP/EN，更新 **Layer 2 `PveEntityState`** |
| **正常了结** | 通关或结算撤退 | 执行幂等奖励发放后，销毁释放内存 |
| **异常中断** | 断连、无心跳、杀后台 | 内存对象直接销毁丢失，视为探索失败（临时背包清零） |

### 7.3 极简架构：断线即失败 (Disconnect = Fail)

根据系统高层架构精简原则，PVE 系统**完全放弃复杂脆弱的断线重连、进度暂存机制与 TTL 落库设计**：
- **纯内存推演**：从进入节点至撤退/通关结束，所有战斗血量、事件推进、临时包掉落均仅存在于服务器的高速内存缓存（如 Redis 或 App 进程空间）中。
- **无情的心跳刀**：客户端必须维持规律的心跳汇报。一旦失去网络连接、超时跌落、或被强制杀死后台，系统立刻销毁该 `PveSession`。
- **天然的惩罚回退**：不需要写复杂的"战败善后"逻辑。由于该进程被直接内存抹除，且一切产出都尚未落入玩家的物理库，所谓的"彻底失败惩罚"随着内存回收自然生效，架构极致清爽。

---

> **状态层**：
> ```python
> # 内存中的 PVE 会话对象（断线即丢失）
> PveSession:
>     event_sequence: EventSequence          # 事件序列 + 当前索引
>     squad_state: PveSquadState             # Layer 1(配置快照) + Layer 2(状态代理)
>     pending_rewards: List[Item]            # 临时背包（风险存放栈）
>
> # 数据库审计流水（永久保留，防并发）
> PveRewardLedger:
>     session_id: UNIQUE                     # 幂等性硬防线
>     rewards_summary: JSON                  # 结算快照
> ```
>
> **行动层**：`PveSessionManager` 负责在内存池调拨构建与销毁操作；外部心跳监控器（Heartbeat）定时轮询死链并触发销毁。
>
> **事件处理层**：心跳丢失 → 销毁内存 → 进度消失即败北；正常通关结算 → 发放凭证落盘 → 回收内存。

## 8. 开发实施路径 (Implementation Roadmap)

放弃图形化点阵地图后，以下模块无需开发：BFS 寻路、图论邻接表建模、战争迷雾、前端地图渲染、Tile 连通性校验。

保留并需实现的核心系统：战斗引擎桥接、三层快照状态继承、收益结算、幂等防护。

### Phase 1: 核心状态机 (Skeleton & Mocking)

首要目标是跑通**"进入区域 → 生成序列 → 遭遇战 → 血量扣除 → 继续推进"**这条最小内循环，不连接任何真实数据库持久化。
- 使用 `MockMothershipService` 和 `MockMechaState` 替代真实的母舰状态和装备配置，避免被周边系统未就绪所阻塞。
- 实现 **Layer 1 配置快照**的深拷贝机制。
- 实现 **Layer 2 状态代理**的战后提取逻辑。
- 所有状态仅存活于内存对象，跑通核心逻辑后再接驳基础设施。

### Phase 2: 基础设施接驳 (Infrastructure Hookup)

- 在正式写结算逻辑前，先实现全局性的幂等性工具（如 `IdempotencyKeyManager`），再复用于 PVE 结算场景。
- 实现心跳监控机制，确保"断线即失败"的架构得以执行。
- 使用依赖注入将 `PveSessionManager` 与数据库连接。

### Phase 3: 三级空间与子区域系统 (Zone & Progression)

- 实装 L2 战术层：子区域解锁链、概率隐藏节点生成与持久化。
- 接入真实的 `user_pve_progress` 进度表，驱动前端战术界面的节点状态显示。
