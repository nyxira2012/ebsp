## 1. 核心设计思想：三层数据生命周期

这是 v1.2 → v2.0 最关键的认知升级。处理与机体相关的数据，始终要区分三层：

| 层级 | 存储位置 | 生命周期 | 负责内容 |
| :--- | :--- | :--- | :--- |
| **静态配置层** | `data/*.json` 文件 | 随版本迭代更新 | 机体原始数值、武器基础属性（全局共享） |
| **用户养成层** | 数据库（关系型表） | 随玩家操作变化 | 改造等级、获得的装备、编队阵容 |
| **运行时快照层** | 内存对象 (`MechaSnapshot`) | 单次战斗期间 | 最终计算后的属性，含 buff/debuff 状态 |

**原则：运行时快照不应被持久化为"存档"。** 它应在每次战斗开始时由工厂动态组装，而非读取一个过去的静态快照，否则版本更新后旧存档数据就会与游戏配置产生矛盾。

## 2. 数据库 Schema 设计

### 2.1 用户资产表（User Asset Tables）

不再使用单一 `game_saves` 表来存储所有信息，而是为每类资产建立独立的表：

- **`user_mechas`** — 玩家拥有的机体，外键关联 `users.id`，`upgrades` 字段（JSON）存储改造进度
- **`user_pilots`** — 玩家拥有的驾驶员，`progression` 字段（JSON）存储等级、经验等
- **`user_equipments`** — 玩家拥有的装备资产实体。除 `random_stats` 字段（JSON）存储专属随机词条外，系统采用“外键物理关联”的方法解决实体归属绑定。通过声明它正在装备至的具体哪一台 `user_mechas` 的数据表主键，协同标明具体的挂载槽位标签，实现装备资产独立存在且可被多台机具稳定建立一对多关系。**注意：不依赖数据库层面的级联解绑，废弃 `SET NULL`。** 一切卸装必须通过业务代码显式的更新与背包容量校验。
- **`user_squads`** — 出战编队，`mecha_ids` 字段（JSON）存储当前上阵的机体 ID 列表，`is_active` 标记出战中的队伍

**设计关键**：每张表只存储**变化的数据**（养成进度），不变的基础数值仍从 JSON 配置读取。

### 2.2 战斗录像表 (`battle_records`)

这是唯一合法存储完整 `MechaSnapshot` 的地方。目的是「冻结」当时的战斗状态，确保历史录像不受未来平衡性改动影响。

### 2.3 JSON 列的使用原则

使用 SQLAlchemy 的 `JSON` 列（在 PostgreSQL 上自动映射为 `JSONB`）来存储养成数据，优点是：
- **无 Migration 代价地扩展字段**：新增一个改造项，只需修改 Pydantic 模型并设置默认值，不需要改表结构
- **一行数据拿全所有养成信息**：无需复杂 JOIN，`SELECT * FROM user_mechas WHERE id = ?` 即可

## 3. 快照工厂（SnapshotFactory）

### 工厂架构

项目的核心工厂是 **`src/factory.py` (MechaFactory)**，负责将静态配置（MechaConfig + PilotConfig + SubPilotConfig + EquipmentConfig）聚合为 MechaSnapshot。它支持完整的属性拼接：驾驶员/副驾驶属性聚合、装备修正、槽位验证、技能收集、升级加成等。

`src/core/factory.py` 中的 **SnapshotFactory** 是用户系统引入后添加的数据库集成层，负责从 DB 读取用户养成数据再组装快照。

> ⚠️ **当前状态**: SnapshotFactory 内部重复了一份简化版的属性拼接逻辑，而非复用 MechaFactory。后续应重构为 SnapshotFactory 仅负责"从 DB 取数据"，核心组装逻辑统一委托给 MechaFactory。

### 快照生成流程

`SnapshotFactory.create_combat_snapshot()` 是战斗前的必经步骤：

1. **查 DB 基础养成**：拿到玩家对该机体的养成数据（改造等级）聚合。
2. **查 JSON 配置**：提取机体模板定义的原始基础静态数值面板。
3. **外键追溯联查（全装备检出）**：根据建立的主外键物理关联关系，要求必须拦截提取该 `user_mechas` 所绑定关联的所有当前存在、且状态正常的 `user_equipments` 资产记录。提炼解析它们附带的独占性词条列表和面板增益。
4. **移交内核进行统一运算合并**：业务层不得自行做算术游戏。必须将被检出的机体基础属性、成长累积加成、外部装备携带参数整体输送并委托给最原初的下层级工厂计算模块，确保所有维度得到一次性纯几何求和或乘积计算。
5. **Apply Traits**：通过已有的 `TraitManager` 注入被动技能运行状态。
6. **返回 `MechaSnapshot` 黑盒**：生成不可逆的独立数值结果结构。直接投喂给战斗引擎，让实战系统不再受反向数据溯源耦合影响。

MechaFactory 是静态配置层和用户养成层的"汇合点"，使两层可以完全独立迭代。

## 4. Repository 层的职责划分

- **`UserRepository`**：用户账户 CRUD（注册、登录验证）
- **`UserAssetRepository`**：用户资产 CRUD（机体、飞行员、装备、编队的增删改查）

Repository 只负责数据库读写，**不做业务计算**。数值合成的逻辑全部属于 `SnapshotFactory`，避免职责混乱。

## 6. 基础设施决策

| 决策项 | 方案 | 理由 |
| :--- | :--- | :--- |
| **Schema 管理** | `Base.metadata.create_all`，无 Alembic | 开发阶段"删库重启"成本极低 |
| **本地数据库** | SQLite (`aiosqlite`) | 零配置，快速开发 |
| **生产数据库** | PostgreSQL | JSONB 支持、可靠性 |
| **异步测试隔离** | `StaticPool` | 保证内存数据库所有 Session 共享同一实例 |

| **幂等性保护** | 幂等性键表 + 装饰器 | 通用防刷基础设施，服务PVE/商店/抽卡等场景 |

## 8. 幂等性基础设施

### 8.1 设计背景

网络环境下客户端请求可能因超时、抖动等原因触发重试。若服务端缺乏幂等性保护，会导致重复执行业务逻辑（如重复发放奖励），造成经济系统膨胀或数据不一致。

**核心问题**：如何确保"同一个操作"只被执行一次？

**适用场景**：PVE收益提取、商店购买、抽卡、任何涉及资产转移的操作

### 8.2 幂等性双轨制防御体系 (Dual-Track Defense)

系统应根据场景的敏感度，采用“API 级装饰器”与“业务级流水表”双轨制：

#### 模式 A：API 级通用状态幂等 (API-Level Stateful Idempotency)
- **实现方式**：通用幂等键表 + `@idempotent` 装饰器。
- **核心逻辑**：在业务逻辑执行**前**拦截。查询 `idempotency_keys` 表，根据 `PENDING/SUCCESS` 状态决定是阻塞、返回缓存响应还是放行。
- **适用场景**：所有 API 接口防连点、防止由于网络超时重试导致逻辑被多次触发（如“进入副本”、“开始移动”）。

#### 模式 B：业务级结算流水幂等 (Business Ledger Hard Idempotency)
- **实现方式**：业务流水表（如 `pve_reward_ledger`）+ 数据库 **Unique Index (唯一索引)**。
- **核心逻辑**：在业务提交事务**中**拦截。通过在流水表中将业务关键主键（如 `session_id`）设为唯一索引，并在代码中捕获 `IntegrityError`。
- **适用场景**：P0 级资产变动（PVE收益提现、商店购买、抽卡发奖）。
- **优势**：它是物理层面的“终极防线”，不受缓存失效或分布式锁失效影响，彻底杜绝“双倍奖励”等极端风险。

**方案选型建议**：一般业务仅使用模式 A；涉及资产入库的敏感业务**必须**强制配套模式 B 作为硬核保护。

### 8.3 数据模型与最佳实践 (Best Practices)

#### 1. 通用幂等键表 (`idempotency_keys`)
用于模式 A。记录生命周期极短，配合 TTL 定时清理。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(64) | 幂等性键（主键），客户端传入或 UUID 生成 |
| `status` | VARCHAR(20) | 状态：`PENDING` / `SUCCESS` / `FAILED` |
| `response` | JSON | 成功后的缓存响应内容 |
| `expires_at` | TIMESTAMP | 过期时间（通常 24h） |

#### 2. 业务流水表 (以 `pve_reward_ledger` 为例)
用于模式 B。记录永久保存（或归档），作为资产变动的核心审计流水。

| 字段 | 类型 | 说明 |
|------|------|------|
| `session_id` | INT | **[Unique Index]** PveSession 的主键，确保一个会话只能结算一次 |
| `user_id` | INT | 所属用户 |
| `rewards_summary`| JSON | 结算时的收益快照 |

**唯一约束实现方案**：
```sql
-- PostgreSQL / SQLite
CREATE UNIQUE INDEX uq_ledger_session ON pve_reward_ledger(session_id);
```

#### 状态转换规则

```
[创建] → PENDING → 执行业务逻辑 → SUCCESS（缓存响应）
                     ↓
                  FAILED（允许重试，删除记录）
```

**状态语义**：
- `PENDING`：请求处理中，拒绝重复提交
- `SUCCESS`：请求成功，返回缓存的响应
- `FAILED`：请求失败，允许客户端重试

### 8.4 装饰器设计思路

#### 处理流程

1. **键提取**：从请求参数或请求头获取幂等性键，若不存在则自动生成 UUID
2. **存在性检查**：查询数据库，判断键是否已被使用
3. **状态分支处理**：
   - 存在且 `SUCCESS` → 直接返回缓存的响应
   - 存在且 `PENDING` → 抛出"处理中"异常
   - 存在且 `FAILED` → 删除旧记录，允许重试
   - 不存在 → 创建新记录（`PENDING` 状态）
4. **业务执行**：调用实际业务逻辑
5. **结果处理**：
   - 成功 → 更新状态为 `SUCCESS`，缓存响应
   - 失败 → 更新状态为 `FAILED`

#### 装饰器接口

```python
@idempotent(endpoint="pve.claim_rewards", ttl_hours=24)
async def claim_rewards(session: AsyncSession, user: User, ...):
    # 业务逻辑
    pass
```

**参数说明**：
- `endpoint`：接口标识，用于日志和统计
- `ttl_hours`：记录保留时间，过期后可复用键
- `key_param`：幂等性键的参数名（默认 `idempotency_key`）

### 8.5 TTL 清理策略

幂等性记录不应无限累积，需要定期清理：

**清理时机选择**：
- 定时任务：每小时执行一次，清理过期记录
- 惰性清理：查询时顺带清理过期记录（性能影响）
- 数据库事件：PostgreSQL 可用 pg_cron 扩展

**推荐方案**：定时任务 + 批量删除，避免单个事务过大

```sql
-- 伪代码示意
DELETE FROM idempotency_keys
WHERE expires_at < NOW()
LIMIT 10000;  -- 分批执行
```

### 8.6 客户端集成规范

#### 客户端职责

1. **键生成**：使用 UUID v4 或类似随机生成器
2. **键传递**：建议通过请求头 `Idempotency-Key` 传递
3. **重试策略**：收到 5xx 错误时可安全重试，使用相同键
4. **超时处理**：键默认保留 24 小时，过期后可重新使用

#### 安全建议

- 键应具备足够的熵（UUID v4 足够）
- 不要使用可预测的序列（如时间戳 + 用户ID）
- 敏感操作建议服务端生成键而非客户端

> [!NOTE]
> **幂等性测试**: 测试幂等性装饰器时，需验证以下场景：
> 1. 正常请求 → 成功 → 重复请求 → 返回缓存结果
> 2. 正常请求 → 处理中 → 重复请求 → 拒绝（PENDING状态）
> 3. 正常请求 → 失败 → 重复请求 → 允许重试（FAILED状态）
> 4. 过期键 → 允许重新使用

## 10. PVE 会话管理：简化方案

### 10.1 设计原则

PVE讨伐战系统采用**"断线即失败"**的简化策略，避免复杂的服务端会话持久化：

| 场景 | 处理方式 |
|------|----------|
| 进入地图 | 内存中创建 `PveSession` 对象 |
| 正常探索/战斗 | 内存状态维护 |
| 正常结算 | 幂等性保护下写入DB |
| **断线/超时** | **直接判定任务失败，清空临时背包** |
| 主动撤离 | 正常结算后退出 |

### 10.2 核心理念

与Doc 7的"运行时快照不应持久化"原则一致，PVE会话同样**不进行服务端持久化**：

```
连接断开 → 内存释放 → 任务失败 → 玩家回到初始状态
```

**设计权衡**：
- ❌ 放弃：断线重连、进度恢复、24小时TTL存档
- ✅ 获得：架构简洁、开发快速、测试容易、无幂等性复杂度

### 10.3 内存会话对象设计

`PveSession` 是纯内存对象（Pydantic模型），不对应数据库表：

```python
class PveSession(BaseModel):
    """纯内存PVE会话对象，不持久化"""
    session_id: str  # UUID，用于幂等性键生成

    # 用户与区域
    user_id: int
    region_id: str

    # 地图状态（纯内存，断线丢失）
    current_layer: int
    map_graph: MapGraph
    explored_nodes: Set[str]

    # 实体状态（百分比存储，用于重建快照）
    entity_states: Dict[str, PveEntityState]  # 己方+敌方HP/EN百分比

    # 临时背包（纯内存，断线清零）
    pending_rewards: List[Item]

    # 会话元数据
    state: Literal["exploring", "in_combat", "completed", "failed"]
    created_at: datetime
```

### 10.4 与快照系统的对接

状态继承遵循Doc 7的三层架构，**不破坏"单局快照生命周期"**原则：

```
战前重建：
DB养成数据 + PveEntityState.hp_pct → 注入 → 新MechaSnapshot

战后提取：
MechaSnapshot.current_hp / max_hp → 百分比 → 保存到PveEntityState
```

**关键点**：`MechaSnapshot` 依然是单局生命周期的临时对象，`PveEntityState` 只是轻量级的百分比容器（类似进度条而非完整快照）。

### 10.6 连接管理

服务端检测到以下情况时直接销毁会话：
- WebSocket连接断开
- HTTP请求超时（如30秒无心跳）
- 客户端主动发送"放弃任务"请求

**无需复杂的TTL机制**，连接断开即意味着任务失败。

### 10.7 实现建议

1. **会话存储**：使用全局字典 `active_sessions: Dict[str, PveSession]`，或连接级别的上下文存储
2. **会话获取**：通过依赖注入 `get_pve_session()` 从当前请求上下文获取
3. **会话销毁**：连接断开时显式调用 `del active_sessions[session_id]`
4. **测试策略**：Mock连接断开场景，验证会话正确销毁且临时背包未写入DB

### 11.2 无出战编队语义（400 化 + 结构化错误分流，批A）

**机器可读错误码**：400/409 响应 `detail` 为结构化对象 `{ "code": ..., "message": ..., ... }`，前端按 code 分支跳转，message 仅人读（401 结构随批B Doc 14 补注统一冻结）。

**simulate（`use_user_save_for_a/b=true` 时）**（v2.4 修订：编队暂不开放，出战机体=持有清单取首台）：
- 当前用户**无任何机体** → **400 `STARTER_NOT_CLAIMED`**，message 指引前往整备库领取初始机体——前端以此引导，**不再降级演示局**（两段式废除，2026-09-22 用户裁决）；
- **有机体即出战**（v2.4）：A 位=持有首台（`list_user_mechas` 按 id 升序）、B 位=次台（仅一台复用首台）——编队不参与战斗装配，`NO_ACTIVE_SQUAD` 自本通道退役。不再静默回退请求配置机体（存档数据缺陷的静默降级语义不变，Doc 14 §2）。
- **纯配置请求不受影响**（D7 沙盘推演语义）：登录用户不勾 `use_user_save` 时可显式模拟任意机体配置——simulate 纯计算不读不写账户资产，是金样张（conftest 直构路径，不经 HTTP）/调试/未来推广试玩局（Doc 16 D1 演进位）的技术底座。**新号动线**：未领取 → 前端引导整备库领取后开自己的机体（练习场不再提供领取前演示局）。

**PVE enter-region（锁队语义）**：
- `locked_mechas` 为空时取当前出战编队；无有效出战编队 → 同上两码分流 **400**。
- `_prepare_locked_config` 的 `DEFAULT_PLAYER_MECHA_ID`（`"rx78"` 假 ID）静默回退路径**废除**；锁定配置为空 → ValueError（端点翻译 400）。
- **build_pve 双保险**（侦察员 F1）：`src/combat/entry.py` 三处 `DEFAULT_PLAYER_MECHA_ID` 回退同步废除，缺配置/缺成员显式 ValueError（enter 期 400 后不可达，触发即缺陷）。

**Doc 16 §2.1 联动**："匿名或无有效存档时静默回退演示配置"降级臂整体修订——匿名臂死于 §11.1，无存档臂死于本条（批B随 Doc 16 升版落字）。

### 11.2.1 开发期放宽：编队不强制（v2.3，2026-09-21 用户裁决）

**动机**：项目处于开发期，编队设置不应成为进入战斗的前置障碍——开发/联调/演示需要随时可玩，先跑通战斗链路，编队正式化（阵位、轮换等）另行演进。

**PVE enter-region**：
- `assert_squad_ready` 前置校验**从 enter 通道拆除**（`src/api/pve_api.py`）；`STARTER_NOT_CLAIMED` / `NO_ACTIVE_SQUAD` 两码在 enter 通道停用。
- `_prepare_locked_config` 回退链恢复并修正：未锁定机体 → 取出战编队 → 仍无有效编队 → **回退演示机体 `mech_rx78`**（静态配置快照，条目无 `user_mecha_id`，与养成快照天然区分）。
- **v2.2 拆除的 "rx78" 假 ID 定性修正**：v2.2 的诊断是"回退本身是地雷"；真实地雷是旧实现写了 `get_mecha_config("rx78")`（配置真实 ID 为 `mech_rx78`），回退永远 KeyError 静默落空、产出空锁定配置。回退语义本身在开发期是合理的，本次以**正确 ID** 恢复。
- 演示机体配置也缺失 → 仍 ValueError（端点翻译 400），定位为缺陷级。

**保留不变**：
- `locked_mechas` 显式指定的归属校验（400 `MECHA_NOT_OWNED`）——防借道他人机体，与编队是否强制无关；
- `build_pve` 缺配置/缺成员的显式 ValueError（缺陷级双保险）；
- **simulate 的 `use_user_save` 通道**：v2.4 起门槛=持有机体（无机体 400 `STARTER_NOT_CLAIMED`），编队不再参与（§11.2.2）——存档覆盖是玩家显式勾选，静默降级会违背显式请求的口径不变；
- 归属校验全量保留：建队/部署/PVE 会话属主口径不放宽；
- claim-starter、`/user/me` 引导状态位（`has_mecha` / `has_active_squad`）照旧——引导信息仍在，只是不再拦截。

**转正条件**：编队玩法正式化（阵位/轮换立项）时恢复 enter 通道前置校验，本节随即废除。

### 11.2.2 编队暂不开放：出战机体=玩家持有机体（v2.4，2026-09-22 用户裁决）

**动机**：编队功能暂不开放（无编队 UI、编队不作为任何出战门槛）；所有对战/练习一律开玩家配备的机体——有机体就开自己的，没有就引导玩家前往整备库驾驶可出动机体。v2.2 批A 的 D3「无编队 400 化」裁决在战斗路径整体废止。

**落地**：

### 11.3 PVE 会话属主校验（统一入口，批A）

### 11.4 初始机体免费领取（死锁破除通道，批A）

```
POST /user/mechas/claim-starter
```

- **前置**：强制登录。
- **并发防线**：事务内对 users 行 `with_for_update()` 串行化同用户并发领取（`MothershipRepository.get_by_user_id(for_update=True)` 同款先例）；名下已有任意 `user_mechas` → **409 `STARTER_ALREADY_CLAIMED`**，detail 附当前首机与出战编队摘要（终态等价成功语义：超时重试撞 409 时前端据此自愈展示，不弹"领取失败"）。
- **授予**：`mech_grunt`（旧式防卫工兵）一台，零改造初始（复用 `create_user_mecha`，mecha_id 即配置 ID）。免费位给最弱杂兵机：招牌机体留给未来卡池，不提前白送贬值。
- **编队防御性补齐（评审刺客 B3）**：名下**无编队** → 建「默认编队」（含该机）并 `set_active_squad` 激活；**已有编队** → 将该机塞入首个编队（不在则追加）并激活之——不新建、不重名。授予与建队同一事务、一次 commit。
- **响应**：`{ "mecha": UserMechaDB, "squad": UserSquadDB }`。
- **新号动线**（v2.4 修订）：注册 → 登录 → 前往整备库领取（机体+编队一步到位）→ 所有对战/练习开自己的机体；未领取时练习场引导前往整备库（不再演示局可玩，§11.2.2）。`GET /user/me` 响应扩 `has_mecha` / `has_active_squad` 状态位，前端据此主动触发引导（战斗就绪判定自 v2.4 起只看 `has_mecha`）。
- **演进位**：经济 MVP（roadmap §7）立项时重裁本接口退役/转新手任务奖励（含"先买后领"语义）。

### 11.5 账户隔离不变量（含现状修补项）

- **数据层**：资产表（`user_mechas` / `user_pilots` / `user_equipments` / `user_items` / `user_squads` / `user_motherships` / `battle_records` / `user_pve_progress` / `pve_sessions` / `pve_reward_ledger`）全量以 `user_id` 外键锚定——现状已达标，升格为**不变量**：新增资产表必须遵守。
- **API 层**：一切资产读写路径必须携带属主上下文；禁止"仅凭资源 ID 即可读写"的端点。
- **引用完整性**（评审刺客 B7）：编队写入（`create_user_squad`）须全量校验 `mecha_ids` 归属，他人机体 ID → **400 `MECHA_NOT_OWNED`**——防止借编队引用以他人养成资产出账。
- **现状修补项**（侦察员 F2/F3，随批A）：`set_active_squad` SELECT 补 `user_id` 过滤（现状可激活他人编队）；`get_active_squad` 改 `.first()` 防存量双激活 500。
- **新端点红线**：API 评审必查项——「属主校验了吗」「引用完整性校验了吗」。

### 11.6 Token 生命周期（维持现状，演进位）

- 7 天 JWT、无 refresh、无登出黑名单——维持。已签发 Token 服务端无法作废，为**已知且接受**的限制。
- **PVE 会话中 401 约定**：心跳 401 不计入会话销毁判定（销毁以连接存活为准），避免"Token 过期→重登耗时→会话误杀清背包"链路；Token 机制本身不动。
- 触发点（届时立项）：GM 后台立项（封号需立即生效）或首个真实客户端上线（不可信设备登录）。
