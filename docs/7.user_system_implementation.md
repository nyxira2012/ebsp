# 7. 用户系统与持久化存档实现计划 v2.1

> **版本说明**:
> - **v1.2**: 单一 `GameSave` 快照方案
> - **v2.0**: 混合关系型架构（Mixed Relational Architecture），三层数据生命周期
> - **v2.1**: 新增幂等性基础设施，完善防刷机制设计

---

## 1. 核心设计思想：三层数据生命周期

这是 v1.2 → v2.0 最关键的认知升级。处理与机体相关的数据，始终要区分三层：

| 层级 | 存储位置 | 生命周期 | 负责内容 |
| :--- | :--- | :--- | :--- |
| **静态配置层** | `data/*.json` 文件 | 随版本迭代更新 | 机体原始数值、武器基础属性（全局共享） |
| **用户养成层** | 数据库（关系型表） | 随玩家操作变化 | 改造等级、获得的装备、编队阵容 |
| **运行时快照层** | 内存对象 (`MechaSnapshot`) | 单次战斗期间 | 最终计算后的属性，含 buff/debuff 状态 |

**原则：运行时快照不应被持久化为"存档"。** 它应在每次战斗开始时由工厂动态组装，而非读取一个过去的静态快照，否则版本更新后旧存档数据就会与游戏配置产生矛盾。

---

## 2. 数据库 Schema 设计

### 2.1 用户资产表（User Asset Tables）

不再使用单一 `game_saves` 表来存储所有信息，而是为每类资产建立独立的表：

- **`user_mechas`** — 玩家拥有的机体，外键关联 `users.id`，`upgrades` 字段（JSON）存储改造进度
- **`user_pilots`** — 玩家拥有的驾驶员，`progression` 字段（JSON）存储等级、经验等
- **`user_equipments`** — 玩家拥有的装备资产实体。除 `random_stats` 字段（JSON）存储专属随机词条外，系统采用“外键物理关联”的方法解决实体归属绑定。通过声明它正在装备至的具体哪一台 `user_mechas` 的数据表主键，协同标明具体的挂载槽位标签，实现装备资产独立存在且可被多台机具稳定建立一对多关系。**注意：不依赖数据库层面的级联解绑，废弃 `SET NULL`。** 一切卸装必须通过业务代码显式的更新与背包容量校验。
- **`user_squads`** — 出战编队，`mecha_ids` 字段（JSON）存储当前上阵的机体 ID 列表，`is_active` 标记出战中的队伍

**设计关键**：每张表只存储**变化的数据**（养成进度），不变的基础数值仍从 JSON 配置读取。

### 2.2 战斗录像表 (`battle_records`)

这是唯一合法存储完整 `MechaSnapshot` 的地方。目的是「冻结」当时的战斗状态，确保历史录像不受未来平衡性改动影响。

### 2.3 JSON 列的使用原则

使用 SQLAlchemy 的 `JSON` 列（在 PostgreSQL 上自动映射为 `JSONB`）来存储养成数据，优点是：
- **无 Migration 代价地扩展字段**：新增一个改造项，只需修改 Pydantic 模型并设置默认值，不需要改表结构
- **一行数据拿全所有养成信息**：无需复杂 JOIN，`SELECT * FROM user_mechas WHERE id = ?` 即可

## 3. 快照工厂（SnapshotFactory）

### 工厂架构

项目的核心工厂是 **`src/factory.py` (MechaFactory)**，负责将静态配置（MechaConfig + PilotConfig + SubPilotConfig + EquipmentConfig）聚合为 MechaSnapshot。它支持完整的属性拼接：驾驶员/副驾驶属性聚合、装备修正、槽位验证、技能收集、升级加成等。

`src/core/factory.py` 中的 **SnapshotFactory** 是用户系统引入后添加的数据库集成层，负责从 DB 读取用户养成数据再组装快照。

> ⚠️ **当前状态**: SnapshotFactory 内部重复了一份简化版的属性拼接逻辑，而非复用 MechaFactory。后续应重构为 SnapshotFactory 仅负责"从 DB 取数据"，核心组装逻辑统一委托给 MechaFactory。

### 快照生成流程

`SnapshotFactory.create_combat_snapshot()` 是战斗前的必经步骤：

1. **查 DB 基础养成**：拿到玩家对该机体的养成数据（改造等级）聚合。
2. **查 JSON 配置**：提取机体模板定义的原始基础静态数值面板。
3. **外键追溯联查（全装备检出）**：根据建立的主外键物理关联关系，要求必须拦截提取该 `user_mechas` 所绑定关联的所有当前存在、且状态正常的 `user_equipments` 资产记录。提炼解析它们附带的独占性词条列表和面板增益。
4. **移交内核进行统一运算合并**：业务层不得自行做算术游戏。必须将被检出的机体基础属性、成长累积加成、外部装备携带参数整体输送并委托给最原初的下层级工厂计算模块，确保所有维度得到一次性纯几何求和或乘积计算。
5. **Apply Traits**：通过已有的 `TraitManager` 注入被动技能运行状态。
6. **返回 `MechaSnapshot` 黑盒**：生成不可逆的独立数值结果结构。直接投喂给战斗引擎，让实战系统不再受反向数据溯源耦合影响。

MechaFactory 是静态配置层和用户养成层的"汇合点"，使两层可以完全独立迭代。

## 4. Repository 层的职责划分

- **`UserRepository`**：用户账户 CRUD（注册、登录验证）
- **`UserAssetRepository`**：用户资产 CRUD（机体、飞行员、装备、编队的增删改查）

Repository 只负责数据库读写，**不做业务计算**。数值合成的逻辑全部属于 `SnapshotFactory`，避免职责混乱。

---

## 5. 认证机制（JWT）

保持 v1.2 的决策：使用 JWT Token 认证。

- Token 存储在 `Authorization: Bearer <token>` 请求头，避免 Cookie 的跨域问题
- 战斗接口 `/battle/simulate` 支持可选鉴权：未登录用户使用默认静态配置，已登录用户尝试加载出战小队

## 6. 基础设施决策

| 决策项 | 方案 | 理由 |
| :--- | :--- | :--- |
| **Schema 管理** | `Base.metadata.create_all`，无 Alembic | 开发阶段"删库重启"成本极低 |
| **本地数据库** | SQLite (`aiosqlite`) | 零配置，快速开发 |
| **生产数据库** | PostgreSQL | JSONB 支持、可靠性 |
| **异步测试隔离** | `StaticPool` | 保证内存数据库所有 Session 共享同一实例 |
| **密码安全** | `bcrypt` (测试环境降低 rounds) | 不可逆哈希，测试不卡 bcrypt 慢速特性 |
| **幂等性保护** | 幂等性键表 + 装饰器 | 通用防刷基础设施，服务PVE/商店/抽卡等场景 |

## 8. 幂等性基础设施

### 8.1 设计背景

网络环境下客户端请求可能因超时、抖动等原因触发重试。若服务端缺乏幂等性保护，会导致重复执行业务逻辑（如重复发放奖励），造成经济系统膨胀或数据不一致。

**核心问题**：如何确保"同一个操作"只被执行一次？

**适用场景**：PVE收益提取、商店购买、抽卡、任何涉及资产转移的操作

### 8.2 幂等性键机制

#### 核心思想

客户端为每个操作生成唯一的幂等性键，服务端使用该键作为"去重标识"。相同键的重复请求会被识别并拒绝，只返回第一次执行的结果。

**方案选型对比**：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 数据库唯一约束 | 可靠性强，天然去重 | 需额外表/字段 | 强一致性要求 |
| Redis 分布式锁 | 性能高 | 依赖外部服务，复杂度高 | 高并发场景 |
| Token 机制 | 无额外存储 | Token 管理复杂 | 支付回调等 |

**推荐方案**：数据库唯一约束 + 状态机，适合本项目的中小规模场景。

### 8.3 数据模型设计

#### 表结构要点

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(64) | 幂等性键（主键），客户端传入或 UUID 生成 |
| `user_id` | INT | 关联用户，支持查询用户历史操作 |
| `endpoint` | VARCHAR(255) | 接口标识（如 `pve.claim_rewards`） |
| `request_hash` | VARCHAR(64) | 请求参数哈希，防止同一键用于不同参数（可选） |
| `response` | JSON | 缓存的成功响应，重复请求直接返回 |
| `status` | VARCHAR(20) | 状态：`PENDING` / `SUCCESS` / `FAILED` |
| `expires_at` | TIMESTAMP | TTL 过期时间（如 24 小时） |

**索引设计**：
- 主键：`id`（幂等性键唯一约束）
- 复合索引：`(user_id, expires_at)`（用户查询 + TTL 清理）
- 单列索引：`endpoint`（接口维度统计）

#### 状态转换规则

```
[创建] → PENDING → 执行业务逻辑 → SUCCESS（缓存响应）
                     ↓
                  FAILED（允许重试，删除记录）
```

**状态语义**：
- `PENDING`：请求处理中，拒绝重复提交
- `SUCCESS`：请求成功，返回缓存的响应
- `FAILED`：请求失败，允许客户端重试

### 8.4 装饰器设计思路

#### 处理流程

1. **键提取**：从请求参数或请求头获取幂等性键，若不存在则自动生成 UUID
2. **存在性检查**：查询数据库，判断键是否已被使用
3. **状态分支处理**：
   - 存在且 `SUCCESS` → 直接返回缓存的响应
   - 存在且 `PENDING` → 抛出"处理中"异常
   - 存在且 `FAILED` → 删除旧记录，允许重试
   - 不存在 → 创建新记录（`PENDING` 状态）
4. **业务执行**：调用实际业务逻辑
5. **结果处理**：
   - 成功 → 更新状态为 `SUCCESS`，缓存响应
   - 失败 → 更新状态为 `FAILED`

#### 装饰器接口

```python
@idempotent(endpoint="pve.claim_rewards", ttl_hours=24)
async def claim_rewards(session: AsyncSession, user: User, ...):
    # 业务逻辑
    pass
```

**参数说明**：
- `endpoint`：接口标识，用于日志和统计
- `ttl_hours`：记录保留时间，过期后可复用键
- `key_param`：幂等性键的参数名（默认 `idempotency_key`）

### 8.5 TTL 清理策略

幂等性记录不应无限累积，需要定期清理：

**清理时机选择**：
- 定时任务：每小时执行一次，清理过期记录
- 惰性清理：查询时顺带清理过期记录（性能影响）
- 数据库事件：PostgreSQL 可用 pg_cron 扩展

**推荐方案**：定时任务 + 批量删除，避免单个事务过大

```sql
-- 伪代码示意
DELETE FROM idempotency_keys
WHERE expires_at < NOW()
LIMIT 10000;  -- 分批执行
```

### 8.6 客户端集成规范

#### 客户端职责

1. **键生成**：使用 UUID v4 或类似随机生成器
2. **键传递**：建议通过请求头 `Idempotency-Key` 传递
3. **重试策略**：收到 5xx 错误时可安全重试，使用相同键
4. **超时处理**：键默认保留 24 小时，过期后可重新使用

#### 安全建议

- 键应具备足够的熵（UUID v4 足够）
- 不要使用可预测的序列（如时间戳 + 用户ID）
- 敏感操作建议服务端生成键而非客户端

## 9. 质量保证

> [!IMPORTANT]
> **异步 SQLite 内存测试**: 必须使用 `StaticPool` 确保多个 AsyncSession 共享同一内存库，否则每个 Session 会得到一个空数据库。

> [!NOTE]
> **旧存档兼容**：v2.0 采用「删档重开」策略，不保留 `game_saves` 历史数据。正式发布前可根据需要考虑是否补写数据迁移脚本。

> [!NOTE]
> **幂等性测试**: 测试幂等性装饰器时，需验证以下场景：
> 1. 正常请求 → 成功 → 重复请求 → 返回缓存结果
> 2. 正常请求 → 处理中 → 重复请求 → 拒绝（PENDING状态）
> 3. 正常请求 → 失败 → 重复请求 → 允许重试（FAILED状态）
> 4. 过期键 → 允许重新使用

## 10. PVE 会话管理：简化方案

### 10.1 设计原则

PVE讨伐战系统采用**"断线即失败"**的简化策略，避免复杂的服务端会话持久化：

| 场景 | 处理方式 |
|------|----------|
| 进入地图 | 内存中创建 `PveSession` 对象 |
| 正常探索/战斗 | 内存状态维护 |
| 正常结算 | 幂等性保护下写入DB |
| **断线/超时** | **直接判定任务失败，清空临时背包** |
| 主动撤离 | 正常结算后退出 |

### 10.2 核心理念

与Doc 7的"运行时快照不应持久化"原则一致，PVE会话同样**不进行服务端持久化**：

```
连接断开 → 内存释放 → 任务失败 → 玩家回到初始状态
```

**设计权衡**：
- ❌ 放弃：断线重连、进度恢复、24小时TTL存档
- ✅ 获得：架构简洁、开发快速、测试容易、无幂等性复杂度

### 10.3 内存会话对象设计

`PveSession` 是纯内存对象（Pydantic模型），不对应数据库表：

```python
class PveSession(BaseModel):
    """纯内存PVE会话对象，不持久化"""
    session_id: str  # UUID，用于幂等性键生成

    # 用户与区域
    user_id: int
    region_id: str

    # 地图状态（纯内存，断线丢失）
    current_layer: int
    map_graph: MapGraph
    explored_nodes: Set[str]

    # 实体状态（百分比存储，用于重建快照）
    entity_states: Dict[str, PveEntityState]  # 己方+敌方HP/EN百分比

    # 临时背包（纯内存，断线清零）
    pending_rewards: List[Item]

    # 会话元数据
    state: Literal["exploring", "in_combat", "completed", "failed"]
    created_at: datetime
```

### 10.4 与快照系统的对接

状态继承遵循Doc 7的三层架构，**不破坏"单局快照生命周期"**原则：

```
战前重建：
DB养成数据 + PveEntityState.hp_pct → 注入 → 新MechaSnapshot

战后提取：
MechaSnapshot.current_hp / max_hp → 百分比 → 保存到PveEntityState
```

**关键点**：`MechaSnapshot` 依然是单局生命周期的临时对象，`PveEntityState` 只是轻量级的百分比容器（类似进度条而非完整快照）。

### 10.5 结算幂等性

唯一需要防刷的场景是**收益提取结算**：

```python
@idempotent(endpoint="pve.extract_rewards", ttl_hours=24)
async def extract_rewards(
    session: AsyncSession,
    user: User,
    pve_session: PveSession,
    idempotency_key: str  # 使用pve_session.session_id
):
    # 1. 幂等性检查由装饰器完成
    # 2. 事务性写入正式背包
    # 3. 销毁内存中的pve_session对象
```

使用 `pve_session.session_id` 作为幂等性键，确保即使客户端重试也只能领取一次。

### 10.6 连接管理

服务端检测到以下情况时直接销毁会话：
- WebSocket连接断开
- HTTP请求超时（如30秒无心跳）
- 客户端主动发送"放弃任务"请求

**无需复杂的TTL机制**，连接断开即意味着任务失败。

### 10.7 实现建议

1. **会话存储**：使用全局字典 `active_sessions: Dict[str, PveSession]`，或连接级别的上下文存储
2. **会话获取**：通过依赖注入 `get_pve_session()` 从当前请求上下文获取
3. **会话销毁**：连接断开时显式调用 `del active_sessions[session_id]`
4. **测试策略**：Mock连接断开场景，验证会话正确销毁且临时背包未写入DB
