# 7. 用户系统与持久化存档实现计划 v1.2

## 1. 基本开发原则：代码级完美适配 (Agnostic Code)
**本项目的核心准则：所有数据库相关的开发必须确保代码在后期无需任何逻辑修改即可适配 PostgreSQL。**

- **数据解耦与复用**: 充分利用 `src/models.py` 已有的 Pydantic 模型作为数据传输对象 (DTO)。`GameSaves` 仅负责透明存储 JSON 快照。
- **工厂模式集成**: `Repository` 在加载存档后，应允许通过 `MechaFactory` 重新注入运行时状态（如 Effects），确保持久化数据与业务逻辑无缝衔接。
- **API 渐进增强**: 保持现有的 `presentation_api.py` 结构，通过 `app.include_router` 模块化挂载新功能，并引入 JWT 守卫现有战斗接口。

## 2. 核心问题汇总与解决策略

| 问题领域 | 解决方式 (方法论) | 关键决定 |
| :--- | :--- | :--- |
| **代码兼容性** | 采用 SQLAlchemy 统一抽象，确保 ORM 逻辑一行不改即可迁移。 | **适配一次到位。** |
| **模型完整性** | 在 `Users` 表预留 `status`, `deleted_at` 等关键字段，支持扩展。 | **初期极简，后期无痛。** |
| **认证机制** | 采用 **JWT Token** 方案。 | **避免 Next.js/FastAPI 跨域 Cookie 限制。** |
| **测试可靠性** | 异步内存测试必须强制共享连接池。 | **使用 StaticPool。** |
| **Schema 管理** | **移除 Alembic**。初期通过 `Base.metadata.create_all` 管理結構。 | **极简组件，删库重启。** |

## 3. 目录结构规划
为了实现“完美适配”和职责分离，必须严格遵循以下结构：

```text
/src
  /database             # 数据库基础设施
    ├── base.py         # 定义 DeclarativeBase 与 AsyncEngine
    ├── models.py       # 存放 User, GameSave 的 SQLAlchemy 映射
    └── session.py      # get_async_session 依赖项 (FastAPI)
  /user                 # 用户领域逻辑
    ├── security.py     # 密码哈希处理 (bcrypt)
    ├── schemas.py      # Pydantic DTO (UserCreate, UserResponse)
    └── repository.py   # 数据库读写封装 (Repository Pattern)
  /api
    └── user_api.py      # FastAPI 路由与认证逻辑
/db                     # 存放本地 .sqlite3 文件 (GitIgnore)
```

## 4. 数据库模型设计

### 4.1 用户表 (Users)
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(32) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    email VARCHAR(255) DEFAULT NULL,    -- 预留
    status VARCHAR(16) DEFAULT 'active', -- 预留
    deleted_at TIMESTAMP DEFAULT NULL,   -- 软删除支持
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.2 存档表 (GameSaves)
```sql
CREATE TABLE game_saves (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    slot_id INTEGER DEFAULT 1,          -- 多存档位 (1-3)
    save_name VARCHAR(100) NOT NULL,
    is_deployed BOOLEAN DEFAULT FALSE,   -- 当前出战标记
    save_data JSON NOT NULL,            -- 通用 JSON 类型
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.2 存档数据结构 (save_data)
`save_data` 字段不仅是简单的 JSON，还包含版本元数据以应对未来的模型变更：
```json
{
    "version": "1.0",
    "mecha": { ...MechaSnapshot.model_dump(mode='json')... },
    "metadata": {
        "summary": "RX-78-2 Level 15",
        "last_area": "Side 7"
    }
}
```
通过 `MechaSnapshot(**data['mecha'])` 可瞬间还原为现有的业务对象。

## 5. 现有系统集成方案

### 5.1 与 src/models.py 集成
- **序列化**: `Repository` 使用 `mecha.model_dump(mode='json')` 生成入库字典。
- **反序列化**: 从 DB 读取字典后，直接利用 Pydantic 的 `MechaSnapshot.model_validate(data)` 还原。

### 5.2 与 src/api/presentation_api.py 集成
**集成步骤:**
1.  **子路由挂载**: 创建 `src/api/user_api.py`，并在主应用中通过 `app.include_router(user_router, prefix="/user")` 挂载。
2.  **JWT 守卫**:
    - 将现有 `/battle/simulate` 修改为可选鉴权或全鉴权。
    - 使用 FastAPI 依赖注入：`mecha_a = db_save.to_mecha() if user_id else MechaFactory.create_default()`。

### 5.3 认证机制 (JWT Token)
对于前后端分离架构（Next.js + FastAPI），JWT 优于 Session Cookie：
- **无视 CORS 限制**: Token 放在 `Authorization: Bearer <token>` 头部传递，不依赖浏览器的 Cookie 存储策略。
- **扩展性**: 支持未来的微服务或分布式部署。

### 5.2 代码级完美适配 (Agnostic Code)
- **统一类型**: 在 `models.py` 中使用 `sqlalchemy.JSON` 存储战斗快照。
- **异步适配**: 使用 `AsyncSession` 确保不阻塞 FastAPI 事件循环。

## 6. 实施路线图

1.  **Phase 1 (环境与底座)**:
    *   安装核心依赖：`sqlalchemy[asyncio]`, `aiosqlite`, `passlib[bcrypt]`, `python-jose[cryptography]`。
    *   创建 `src/database/base.py`，实现异步引擎初始化与 `Base.metadata.create_all` 逻辑。
2.  **Phase 2 (数据层实现)**:
    *   定义 `models.py` 映射。
    *   实现 `Repository` 层及其对 Pydantic `mode='json'` 的映射逻辑。
3.  **Phase 3 (身份认证与 API)**:
    *   实现 JWT 签发与解析逻辑。
    *   集成 `user_api.py` 到主应用并支持 `Depends(get_current_user)`。

## 7. 质量保证 (单元测试防坑)
> [!IMPORTANT]
> **异步 SQLite 内存测试**: 在使用 `sqlite+aiosqlite:///:memory:` 时，必须显式配置连接池，否则不同的 Session 会连接到不同的内存数据库：
> ```python
> engine = create_async_engine(
>     "sqlite+aiosqlite:///:memory:",
>     poolclass=StaticPool, # 确保所有连接共享同一个内存数据库
> )
> ```

## 8. 运维管理建议 (No-Migration Strategy)
- **开发阶段**: 若修改了 `models.py` 的表结构，只需手动删除 `db/ebsp.sqlite3` 并重启服务，系统会通过 `create_all` 自动重建最新表结构。
- **生产阶段**: PostgreSQL 首次运行时会自动建立完整 Schema。由于开发初期不保留历史数据，此方案最为高效。
