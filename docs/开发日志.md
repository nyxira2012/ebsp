## 2026-09-22 · Doc 17 物品管理系统（mawang 四批交付 df0ed35 / 9ef1524 / 74a561a / 220d647）

### 落点裁决
- **新建 `src/user/item_system.py` 作唯一门面，不在 `inventory.py` 里加**——容量算法服务（占用/准入/批量写入）与资产进出门面（六招+票据+台账+货币+五道检查）是两族职责；前者是"格子的算法"，后者是"家当的门"。塞一起会把 224 行的容量服务撑成 800 行混合体。刺客全量审确认门面 600 行级内聚合理、不拆分（约 1/4 是承重 docstring）。
- **交换不做成门面方法**——交换=调用方在同事务内 `charge_credits` + 玩法入库（母舰购买是样板）；把母舰 owned_ids 写进物品门面反而制造反向依赖。被否方案：门面提供泛化 `exchange()` 原语（本期只有母舰一个用例，抽早了）。
- **mismatch 收场单点 `src/api/errors.py`**——"先 commit 留档再 400"最初在两个 router 各写一份，第三个发放方（claim-starter）落地时收成共享 helper。教训：**发放类语义的收场路径，第二个使用方出现时就该收口**，别等第三个。

### 已知坑
- **identity map 不回填 + `for_update` 锁等待**：锁住 users 行后若该对象已在会话缓存里（关系 lazy="selectin" 常提前加载），SQLAlchemy 不会自动重读最新已提交版本——锁等待横跨他人提交后会拿**过期余额**核对扣减。修法：锁读必须带 `populate_existing`（已下沉 `MothershipRepository.get_by_user_id` 的 for_update 分支与 `ItemSystem._get_user`）；`autoflush=False` 会话下读前还要 flush，否则未落库改动被静默丢弃。批2 实测踩中。
- **`InventoryService.add_assets` 的 OVERFLOW 是返回值不是异常**——吞返回值会让"信用点入账+台账写行+票据转 accepted 而货物没进包"（部分成功）。门面已 fail-closed 接住；**任何新的 add_assets 调用方都必须检查返回值**。
- **rejected 票据不能占回执幂等位**——首版实现把"回执已存在"一律当"已发放"短路，结果清单不符的批次被永久搁浅（重结算直接 200+删会话）。正确语义：rejected 只留档，重交时复检、修复后可置换回 pending。
- **唯一约束并发竞态用 SAVEPOINT**：先查后插在 PostgreSQL 下并发第二路会裸抛 unique 冲突 500。修法：`session.begin_nested()` 内落库，撞唯一回退保存点、按键重查返回竞态对手的行（`ItemSystem._flush_new_ticket`）。
- **mismatch 收场必须先 commit 再 400**：`get_async_session` 依赖对 HTTPException 走 rollback——先抛 400 的话 rejected 留档票据会被一并回滚，违反"留档供对账"。共享收口在 `src/api/errors.py::commit_and_report_mismatch`，新发放来源必须复用。
- **starter 回执的 rejected 复检入口不可达**（记录不修）：claim_starter 有机体即早退，mismatch 后的起步包票据无法经重领复检——但起步清单是代码常量且材料不做模板校验，正常数据无 mismatch 入口；若未来起步包改为可配置，需在早退前补一次复检。
- **环境命令**：本机测试/类型走 `.venv`（uv 不在环境）——`.venv/bin/python -m pytest` / `.venv/bin/pyright`；mawang 的 slice_check 需要 `PATH=".venv/bin:$PATH"` 前置才能找到 pytest。
