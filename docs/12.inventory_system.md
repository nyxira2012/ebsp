## 1. 系统定位

### 1.1 核心职责

背包系统是玩家存储资产的**逻辑中心**。它并不直接负责物理存储（由各资产表负责），而是提供**容量管控、分类统计与合并逻辑**的业务层。

| 职责 | 说明 |
|:---|:---|
| **容量生命周期** | 维护从“获得物品”到“容量检查”再到“超载处理”的完整链路 |
| **状态聚合** | 实时汇总不同资产表（装备、材料、碎片）的占用情况 |
| **堆叠逻辑管理** | 判定不同类型的物品如何占用货舱格子 |
| **超载准入控制** | PVE 结算或商店购买时的强行拦截与清理诱导 |

### 1.2 设计原则

*   **容量来源去中心化**：上限不再由当前出战母舰决定，而是基于玩家的最高资产配置。
*   **非装备优先原则**：已穿戴在机体上的装备视为“离舱状态”，不计入货舱容量。
*   **差异化堆叠**：根据物品稀有度与属性波动性，采用不同的格子占用策略。

## 2. 容量规则与计算逻辑

### 2.1 容量上限 (Capacity Limit)

玩家的背包容量上限由其**所拥有的母舰中 cargo_capacity 属性最高的数值**决定。

*   **逻辑说明**：系统会遍历 `UserMothership` 中已解锁的所有母舰型号，取其配置中的最大货舱容量作为玩家的全局上限。
*   **设计优化**：玩家无需手动切换母舰即可享受已购得的最大载货能力，简化了日常操作。

### 2.2 背包占用 (Occupancy Calculation)

背包总占用数由各分类物品的“占格数”累加而成。只有**未装备 (In Stock)** 的物品计入占用。

#### A. 装备类 (Weapons & Equipment)
*   **特点**：具有随机词条、ilvl、强化等级。
*   **占用逻辑**：**不可堆叠**。
    *   **已装备**：占用 0 格。
    *   **未装备**：每件占用 1 格。

#### B. 材料类 (Alloys, Shards, Relics, etc.)
*   **特点**：无随机词条，同 ID 物品属性完全一致。
*   **占用逻辑**：**按类型堆叠**。
    *   同一类物品（无论数量多少）仅占用 1 格。
    *   物品通过 ID 进行归类。

### 2.3 计算方法（方法论）

1.  **确定上限**：查询玩家所有已购母舰 -> 获取配置 -> 取 `cargo_capacity` 最大值。
2.  **汇总占用**：
    *   统计 `UserEquipment` 中 `is_equipped=False` 的记录总数。
    *   统计 `UserItems`（或材料表）中按 `item_id` 字典去重后的种类总数。
3.  **计算结余**：`可用空间 = 上限 - (离舱装备数 + 材料种类数)`。

## 3. 物品分类映射表

| 物品子类 | 堆叠方式 | 占用计算方式 | 说明 |
|:---|:---|:---|:---|
| **机载武器** | 不可堆叠 | 1 件 = 1 格 | 含有随机 stats，需独立存储 |
| **功能插件/装甲** | 不可堆叠 | 1 件 = 1 格 | 含有随机 stats，需独立存储 |
| **强化合金** | 按类型堆叠 | 1 类 = 1 格 | 无论拥有 1 个还是 999 个，只占 1 格 |
| **机体碎片** | 按类型堆叠 | 1 类 = 1 格 | 无论拥有 1 个还是 999 个，只占 1 格 |
| **古代遗迹/任务物品** | 按类型堆叠 | 1 类 = 1 格 | 通常为唯一或同质化物品 |

## 4. 核心流程设计

### 4.1 准入检查流程 (Admission Control)

系统在任何获取物品的行为发生前执行此流程：

1.  **预计算**：将待获取物品按堆叠规则进行分类，计算它们将新增的格子数。
2.  **容量校验**：判断 `当前已用 + 预增格子 <= 最大上限`。
3.  **分支处理**：
    *   **满足条件**：执行原子写入，操作成功。
    *   **触发超载**：拦截写入流程，标记交易/结算为“挂起状态”，引导至清理界面。

### 4.2 超载处理流程 (Overload Handling)

当结算导致货舱溢出时（如 PVE 战利品回收）：

1.  **挂起进入**：战利品暂存在内存的“临时背包”中，不写入正式数据库。
2.  **强制清理**：弹出 UI 要求玩家处理溢出。玩家可选择：
    *   **出售**：将现有背包中的冗余装备转化为信用点。
    *   **拆解**：获得材料（可能因类别不同而不消耗新格子，或合并占用）。
    *   **丢弃**：直接销毁掉落物。
3.  **最终确认**：只有当 `当前占用 <= 上限` 时，系统才允许关闭清理界面，并将残余战利品正式入库。

## 5. 系统集成方案

### 5.1 与母舰系统的协作

*   **数据订阅**：背包系统不维护母舰列表，而是在计算上限时即时查询母舰系统的资产记录。
*   **配置反馈**：当玩家购买更大型母舰时，前端立即更新背包 UI 的进度条分母。

### 5.2 与 PVE 系统的协作

*   **结算拦截**：PVE 结算 API 负责在写入资产前调用背包系统的校验方法。
*   **断线保护**：若玩家在超载清理界面断线，系统按 Doc 10 的止损策略处理（默认销毁临时背包或将物品发送至待处理邮件）。

---

## 6. 后续扩展方向

*   **容量临时增益**：通过消耗品或技能暂时提升 `cargo_capacity` 上限。
*   **格子解锁机制**：在基础母舰容量之上，允许玩家消耗信用点开启额外的“私人货柜”。
*   **分类视图**：前端通过 `type` 标签自动对物品进行过滤展示（装备页、材料页）。
*   **锁定保护**：为珍贵装备增加锁定标记，防止在超载清理时被意外误售。

## 7. 开发实现与工程防范 (Engineering Risk Mitigation)

基于对系统架构的综合评估，我们在正式开发 Phase 1 之前确立以下防范机制：

### 7.1 数据结构补全 (Data Structure Completeness)
为支持上述堆叠与离舱逻辑，数据库必须满足以下改动（已同步映射至 ORM 代码）：
*   **`UserEquipment` 表**：新增 `is_equipped` 布尔字段。
*   **`UserItem` 表**：新增通用物品表，包含 `item_id`、`quantity` 字段，负责记录材料、合金等堆叠物。

### 7.2 性能与聚合复杂性 (Performance Optimization)
动态计算货舱格子（`COUNT(*)` + `COUNT(DISTINCT item_id)`）在频发获取物品时可能产生性能负担。
*   **当前策略 (Phase 1)**：在初期玩家规模与物品持有量较小时，依然采用实时聚合。
*   **演进策略 (Phase 2)**：当玩家体验受影响时，将引入 `current_occupancy` 冗余字段（缓存），由每次入库/出库行为触发原子更新。

### 7.3 依赖解耦与接口模拟 (Decoupling Incomplete Systems)
背包系统的开发不必等待母舰（Mothership）或 PVE 系统的完工：
*   **依赖抽象**：实现 `IMothershipProvider` 接口用于提取玩家上限，开发期内提供一个永远返回 `100` 的 Mock Provider。
*   **模拟测试环境**：超载和强制拆解逻辑将通过单元测试（手工传入超出上限的 Dummy 数据）进行闭环验证。

### 7.4 事务与状态一致性 (Transactions & Consistency)
*   一旦玩家穿/脱装备，必须通过严格的**数据库事务**确保 `user_squads/user_mechas` 中的装配引用，与 `user_equipments.is_equipped` 状态强同步更新。
*   **并发安全 (Concurrency)**：`UserItem` 表强制实施 `(user_id, item_id)` 联合唯一约束，保障按类堆叠逻辑在并发环境下的原子性。

### 7.5 断线保护与资产持久化 (Persistence & Reconnection)
为彻底解决 7.4 提到的“随内存烟消云散”问题，我们在 Phase 1.5 中引入以下机制：
*   **持久化会话 (PveSession)**：结算战利品直接写入数据库的 `pending_loot` 字段。
*   **断线重连**：若玩家在处理超载时掉线，重登后后端会识别到未完成的 `OVERLOADED` 会话，强制拦截其他路由并重新引导至清理界面。
*   **增强校验**：`finalize_overload` 接口会显式验证丢弃物品的权属与数量，确保玩家无法通过篡改 ID 列表越权操作他人资产或已装配装备。
